# @thenetwork/engine

Matching and opportunity engine v1 prototype (PRD Sections 6, 14, 15, 32.8-32.13, 33). It is a
transparent, testable pipeline. It produces a small number of high-conviction proposals,
explains each one using shareable facts only, never trades hard constraints for score, and logs
everything needed to replay the run.

```ts
import { runEngine } from "@thenetwork/engine";
const { proposals, runLog } = await runEngine(snapshot /* WorldSnapshot | EngineInput */, { seed: 7 }, { llm, embed, judgeCache });
```

- `snapshot` is the core `WorldSnapshot`, optionally extended as `EngineInput` with `events`, `safetyHolds`, `feedback`, `interactions`, `idAliases`, `reliability`, `categoryQuotas` and `exposureDebt`.
- `cfg` is a deep-partial `EngineConfig`, merged over `DEFAULT_CONFIG` in `src/config.ts`. Its hash is logged.
- `deps.llm` turns on the optional judge. `deps.embed` replaces the local hashed embedding. `deps.judgeCache` lets the judge cache persist across runs.
- Proposals are `EngineProposal`, a superset of core `Proposal` that adds `category`, `roles`, `expiresAt`, `anchor`, `via`, `safetyClass`, `threshold`, `channels`, `judged`, `selectorRank` and `selectionProbability`.

Commands:

```bash
pnpm run sim                  # every pack's conformance rules and its world gates, plus the Network sims (scripts/sim.ts)
pnpm run sim --only slop      # one pack (network | slop | peon | friends)
```

## App packs

`runEngine(input, cfg, { pack })` runs one app's matching. A pack (`src/pack.ts` `AppPack`) supplies the ontology (lanes, objectives), eligibility rules, generators, geo, scoring and selection hooks, consent, attention settings, the judge prompts, explanation copy, optional plans and the match vectors (lane memberships, tags, standing); core invariants (minors in no role, blocks, consent before reveal, the leak gate, the judge cannot undo a hard filter) cannot be loosened by a pack. `pnpm run sim` checks them for every pack (scripts/sim/conformance.ts).

The service runs it as the slop app's onboarding loop (`packages/network/service/packs.ts`, `AppHooks.onboarding`), and `pnpm run sim --only onboard` gates it on `evals/slop-onboarding/`. Orientation policy (PRD 40.5): "bi", "pan", "queer", "both" and "a mix" leave who the member seeks unset, and the agent asks who they hope to meet. The founder may still pick the other policy (read those words as a seeking set); it is listed as a founder decision.

slop.date private Date standing has one implementation: `src/packs/slop/standing.ts` (`DateStandings`).

- It builds one rating pool for each market and dating pool from the matching snapshot.
- Each rated adult gets a midrank percentile. The uncertainty comes from the photo count and the spread of the ratings of each photo (spec/memberStanding.md).
- The validity monitor turns the standing off while real outcomes show that the gap predicts nothing (spec/weeklyBias.md).
- A member outside the home market counts in the pool of that market. The pool is not copied.
- The monitor counts each introduction once. The production network writes one check-in record for each member, with the identifier `<introduction>:fb:<member>`.
- The service reads the monitor through `AppWiring.dateStanding` and `NetworkRuntime.dateStanding` for the weekly bias report. The report and its alert line carry only the counts and the decision.
- The Clef question bank (`src/packs/slop/clef.ts`) asks nothing about identity (gender, trans status, orientation, race, religion, disability). It asks nothing about age beyond the adult gate.
- The rating questions ask about the person in the photo, not about what most users of an app prefer. `packages/engine/test/slop-standing.integration.test.ts` checks the bank against a list of forbidden topics.

Results: [slop photo standing](../../docs/results/2026-11-22-slop-photo-standing.md).

The slop.date Date lane's pack value is [spec/datePackValue.md](../../spec/datePackValue.md).

- `src/packs/slop/score.ts` reads a profile into the answers and pair inputs of the spec. Then it calls the generated `datePackValue`.
- `src/packs/slop/packBound.ts` gives the two upper bounds of that spec for the candidate search. `datePackBound(a, b, o)` uses the cheap pair inputs. `datePackClassCap(a, classKey, untouched, o)` is the cap for the partner class `datePackClassKey(b)` (keys `0` to `15`).
- `slopVectors` (`src/packs/slop/generators.ts`) gives the bounds to the match core as `packBound` and `packClasses`. The candidate search uses the pair bound for each touched Date candidate. For the untouched bound in the direction of the searcher, it uses the largest class cap in the window.
- All Date markets of a member share one weekly capacity, which `assign.ts` counts for each member. An open thread already stops the member (rule `your_turn`).
- Appearance ratings count in matching and are never shared (founder decision 2026-10-08). The overall rating is the private Date-lane standing of the member. A rating below `appearance.minConfidence` counts as no rating.
- `appearance.bodyType` selects the partners with a confident rated body type (`minConfidence`). It also sets the shrink of the revealed body-type preference (`revealedShrink`).
- `learned.enabled` turns the revealed-taste factor on or off. Only the pack evaluation sets it to false.

### Stated openness and cofounder facts

The decisions are in [mutual openness](../../spec/mutualOpenness.md) and [cofounder intent](../../spec/cofounderIntent.md); the packs only read tags and call the generated functions.

- Tags. slop: `romance:is:<g>`, `romance:seeks:<g>`, `romance:trans:<yes|no>` (from a stated identity only), `romance:open_trans:<open|not_open|only|declined>` and, for a nonbinary member, `romance:shown_to:<woman|man>`; all agent_private. friends: `friends:gender:<g>` and `friends:open_gender:<women|men>`, agent_private. Cofounder lanes (ntwrk and peon): `cofounder:role:`, `cofounder:commitment:`, `cofounder:idea:`, `cofounder:must:<field>`, `cofounder:prefer:<field>` on matchable facets of the lane's own app.
- Readers. `slop/profile.ts` `datingFactsOf` and `datingStatementOf` (the slop pair rule `orientation_mismatch`, the slop judge's pair check and the ConsentNetwork romance gate before reveal all call `mutuallyOpen` on them); `friends/info.ts` `friendStatementOf` (pair rule `friend_openness`); `network/cofounderFacts.ts` `cofounderFactsOf` (pair rule `cofounder_must_have` and the peon cofounder pair check; preferences become complement offers and seeks).
- Date segment (`slop/generators.ts`). The own key is the member's segment class (which seekers the member appears to, and the stated trans flag) and coarse cell; the partner keys are the classes the member admits, out of all 16, on every cell within the member's limit. A member who dates in several markets gets no segment. The pair rule checks the other direction.
- Friend segment (`friends/vectors.ts`). The own key is home, transit-tolerance class and stated gender. A partner's tolerance is at most the bound of its class and the transit rule never gets worse as a tolerance grows, so every partner the transit rule admits is in a listed (home, class) key; the gender part lists every stated gender the member admits.
- Extraction (`slop/extract.ts`). "trans" and "cis" qualify the next gender word; "not into trans women", "no trans women" and "anyone but trans people" record not open and never exclude the gender itself; "only" inside or after a list of trans-qualified genders records only; "I'm trans" is read only at the end of a clause ("i'm a trans ally" says nothing about the member); the bare answer to the trans question tests a negation before "i am", and "no preference" reads as open; "only trans partners" from a member who did not state trans is not stored (`transAnswerOf`), and while it stands no seeking set is stored either (`seeksAnswerOf`), so both questions are asked again and the member is not matchable; the shown-to answer is read clause by clause and never as a seeking set. The straight default after the last seeks question applies only to a woman or a man who stated no orientation label (founder decision 2026-10-11, narrowed by [slop onboarding](../../spec/slopOnboarding.md)).

### Module notes

The code lines that the 2026-11 work added or changed have no comments (AGENTS.md, Clarity). Older modules (`attention.ts`, `plans.ts`, `config.ts`, `pack.ts`, `relayClef.ts`) still have comments. The rules that a reader of these modules needs are here and in the specs that each module calls.

- `pack.ts`. The core owns the invariants, and the packs own the policy. A pack is data and small, pure, synchronous hooks, called in a fixed order. Pack rules run in addition to the core rules and can only remove candidates. These core invariants hold for every pack:
  1. Blocks win. A blocked or avoided pair is never a warm tie, never paired and never a `via`.
  2. Hard filters run before scoring and before every judge pass. The judge can only remove.
  3. The LeakGuard checks every member-facing string (explanations, probes, the judge "why", questions).
  4. The engine is deterministic: a seeded RNG, a stable order and no clock reads. The same input, config and pack give the same bytes.
  5. Consent comes before reveal. Nobody is named to anyone before the consent flow of the pack allows it.
  6. The age rule of the core (`candidateAgeReason`, below) applies to every pack. `LaneDef.minors` is `"never"` or `"teenFriendship"`, and `validatePack` refuses `"teenFriendship"` outside the categories of `teenFriendCategory`.
- `attention.ts` `buildProbe`. The probe is anonymous and asks for consent first (1.8, D5). It shows only the activity, the time, an area and at most one `shareable` attribute of the other person. It never shows a name, a photo, an employer, or anything `matchable` or `agent_private`. Each candidate text must pass the leak gate (`checkMemberFacing` with `privateVocabulary` of the other people), a name-token check and a check of the employer-like values of the others. If the richest text fails, the probe drops the attribute, then the area. If no text passes, the result is null and nothing is sent. A romance probe says that it is a romance introduction and goes only between adults.
- `plans.ts`. The planner uses public venues and events only, never the home of a member. No money goes through the Network (PRD 32.12). Volunteer shifts at existing organizations are activities. Plans are never romance (category `social`, D15). Blocks, opt-ins, dealbreakers and safety holds come from `filters.ts`. The attention layer and the Network apply the cap and quiet hours. The review judge approves each plan item before its first probe (spec/automatedReview.md). In `planAllowanceConfig` a paused member stays at 0. A plan item of a member aged 13 to 17 passes `itemGate` only when the network sets `teenFriendAllowed`. `PlanRunOpts.canMatch` is the age gate of the bench (backfills and the partner of a partner plan): the caller gives the age rule of its plan, and the run probes no member for whom it is false. Without it the run acts on ids only, because the planner screens every roster. `crewSessionPlan` gives the next session of a crew (the same weekday and time, `cadenceDays` after the last). Each session is opt-in and the hosts rotate. It gives null when the crew is handed off, or when a pair of its members has no pair value in the plans lane today. A crew with a minor also needs its own venue, which must pass `planPlaceOffered`.
- `packs/friends/index.ts` `friendsPack` (PRD 40.2 and 40.6). Groups of 3 to 6 at public venues come first. One-to-one activity partners come second, and only after a group meetup. The probe is anonymous and puts the activity first, with time options; names come only at quorum. The same people meet again near home (`same_table_again`). A crew is offered after one great plan and goes to its own chat after three sessions. The venue keeps the longest transit trip of the group as short as possible. Romance is excluded at every level: no lane, rules for members, pairs and configurations, and no romance words in any copy. Unverified members and members with a safety cue are held.
- `reviewJudge.ts`. The review judge of [automated review](../../spec/automatedReview.md) (owner decisions D15 to D17 of 2026-11-22). The network builds a `ReviewPacket`: the roster, the age facts that code already checked, the plan and every probe and reveal text. `packetSuspect` finds text that speaks to a reviewer or a model before any call. `modelReviewJudge` asks the model with the adult rubric, and with the minor rubric also when the roster has a minor. `parseReviewJudgeReply` reads the reply with a strict JSON reader (key order, depth and length limits) and gives the verdict through the generated `judgeVerdictOf`. A reply that does not parse is `undecided`. `simulatedReviewJudge`, `simulatedServiceJudge` and `holdEveryItem` are the stand-in judges of the simulator and the tests.
- `relayClef.ts`. The production relay classifier is Clef on Workers AI, a decision model. Clef answers a fixed question bank about the text, and the answers are the feature vector. One head for each category gives a score and a threshold (the weight field `hold`). A score at or above the threshold gives `clef:<category>`. For harassment, a threat or slur answer above its minimum gives `clef_severe:<category>`. A low mean confidence with a middling score in a high-risk category gives `clef:uncertain`. Every reason blocks the text, so Clef can never pass an item that the rules stop. The default model is clef-flash. A timeout, an HTTP error or an offline cache miss answers `unavailable`, and the engine blocks the text with `classifier:unavailable` (spec/relayDecision.md). The default timeout is 2500 ms. `onEvent` gets the model, the latency, the token count, the outcome and the categories, never the text.

- `match/run.ts` `MatchRun`. One matching run over a World keeps the profiles, the candidate index and the memoized searches, edges and circles. Every candidate path reads pairs from it, so one pair gate and one search decide every pair. `tally()` gives `runLog.search`. `searchOutcomes()` gives `runLog.searchOutcomes`: one row for each search that closed Budgeted or kept no candidate (member, lane, `empty` or `budgeted`, `unseenBound`), at most 500 rows, highest bound first. The rows are staff-only; the Observatory run summary keeps them (spec/candidateSearch.md).
- `match/profile.ts`. A profile is one lane membership of a matchable member or entity (a member, or a peon job seat that a manager owns). Packs supply the vectors; the engine owns the rest. Tag ids follow the sorted order of the distinct tags, so one run always interns the same way. A segment is a superset of the pack's own pair rules.
- `match/circles.ts` and `group.ts`. The one circle builder forms circles from the lane's bounded search edges at or above the circle pair floor, and `circleCoherent` admits each circle (spec/groupFormation.md). A pair without a value is not counted in the evidence, so `circleCoherent` refuses the circle. Only a Peers lane with a circle maximum forms groups: never romance, never a two-sided lane.
- Pack hard filters (`packs/*/rules.ts`). They run after the core prefixes (members: unknown, underage, safety hold, paused; pairs: duplicate, underage, blocked) and can only remove. The order is the funnel contract: the first failing rule names the reason. friends.help: `romance_excluded`, `unverified` (liveness and age assurance must both pass; only `verify:<check>:pass` counts), `safety_review` (an observed cue holds the member for human review), `reliability` (two no-shows without a completed meetup since), `group_first` (one-to-one only after a group meetup), `transit` (geo). slop.date: stated preferences are filters only (mutual gender and orientation, age ranges both ways, dealbreakers, radius or cities); safety cues and the Network's records hold a member for review; the mutual radius is checked last. ntwrk: `config.romance.requireStatedPrefs` applies to every romance configuration, romance is pairs-only, and help that enters a home needs two or more helpers or helpers who already met the requester (F14). The romance item gates of ntwrk and slop send a romance item only to a member who `canBeMatched` and opted in to romance; an ntwrk view without `categoriesOptIn` has no romance consent.
- `packs/slop/profile.ts`. The dating profile is read from facet tags: `romance:is:`, `romance:seeks:`, `romance:age:<lo>-<hi>`, `slop:zip:`, `slop:area:`, `slop:scope:city|radius:<mi>|multi:<c1>,<c2>`, `slop:max_miles:`, `slop:goal:`, the lifestyle facts (`slop:smoking:`, `slop:drinking:`, `slop:has_kids:`, `slop:wants_kids:`, `slop:religion:`, `slop:religion_importance:`, `slop:politics:`), `slop:dealbreaker:`, `slop:activity:`, `slop:free:<slot>`, `slop:wants:<dim>=<x>`, `slop:self:<dim>=<x>`, `safety:` and `verify:`. There is no race or ethnicity field: tags that look like one (and health, immigration and income tags) are dropped before any rule, score or explanation can read them (PRD 40.5). The attended slot of a completed date is its weekday and hour in the time zone of each member's home city (`localParts`), so an 8 pm New York date is a Monday evening, not a Tuesday. An interest tag that is blank after trimming is dropped, as the postings drop it, so each interest that the Date pack value counts as shared is also a shared posting tag and the untouched class cap stays sound.
- `packs/slop/appearance.ts`, `clef.ts`, `biasMonitor.ts`. Ratings are computed at photo upload, outside the engine run, and stored as agent_private facets (`appearanceFacet`). Every rater refuses a subject who is not `canBeMatched` or whose age is not verified before it reads a photo. A rating is never shared: no score, rank, bucket, body type or derived phrase goes into member-facing text, probes, reveals, explanations, asks, proposals or the run log (`appearanceLeak`). Clef is a decision model: one call per photo (base64, at most `maxPhotos`), the answers to a fixed question bank are the feature vector, and a fitted linear head and a calibration give a z-like score. The bias monitor is admin-only and reports aggregates: outcome rates per member-month by group, with an alert below the four-fifths ratio; groups come from consented self-reports, an audit sample or internal groupings, never from photos or names.
- `packs/slop/extract.ts` and `onboard.ts`. Rules read the onboarding text first; an optional model reader fills only fields the rules left unset. A field is set only from words that state it, with a confidence and an evidence span. Ambiguous words leave the field unset and `nextQuestion` asks. The lowest stated age wins; under 18 sets `minor` (never matchable, no dating question); an explicit age under 13 sets `declined` and clears everything. One question per message; the read-back repeats only what the member said, never identity, orientation, age, kids or faith.
- `packs/slop/judge.ts`. Pass 2 only, and only when an LLM is wired. The context carries stated facts, an age band, a distance band, shared interests and safety signals; never a name, an exact age, a zip, a photo, an appearance rating, a body type or a learned attraction score. The judge can only remove a pair.
- `packs/peon/match.ts`. A job seat of a verified employer is Offering and an adult candidate is Seeking, once for each role family the candidate seeks. Skill levels are one tag per level, and an unverified claim counts one level lower. Standing is the private role level; the pack value is pay, directed. A seat or a candidate without a stated level, family or pay has no membership. `peonSeats` makes a job seat only for a manager whose recorded age is a whole number that `canBeMatched` accepts.
- `packs/network/index.ts` `networkPack`. world.ts, engine.ts, attention.ts and plans.ts import it for their default `pack` argument, so its top level reads only leaf data: it wraps function values from other modules in arrows, and `eligibility`, `generators` and `vectors` are getters, because rules.ts is in the filters and world import cycle. A member aged 13 to 17 can join and use the agent alone (account tier `matchable: false`). The only introduction of a minor is a friendship introduction in the Friend lane (`social`, `minors: "teenFriendship"`), under the age rule below. A minor is never matched for romance or work. The pack has no Date lane, so it asks no romance preference question. The consent default is wanter first, with the booked plan as the reveal and an easy opt-out. A romance item goes only to an adult who opted in to romance; a view without `categoriesOptIn` has no romance consent. `NETWORK_PACK_VERSION` is not written to the run log.
- `packs/peon/seats.ts`. In the service a hiring manager is one member, and each job is one intent (category professional, details `peon:job ...`) whose facets carry `peon:posting:<intent id>`. `peonSeats` (service snapshot, app peon) makes one seat member `job:<intent id>` for each posting, with the posting's facets and intent, the manager's company facts (company, verified, safety cues), presence and blocks, so a candidate who blocked the manager never sees the manager's jobs. The posting rows leave the manager, who can also be a candidate. The seat holds `peon:openings:<n>`, the posted headcount (1 when none is stated, 0 when the posting is not active), and `seatOwner`, which the service uses to route the probe and the intro; the engine never reads it. `peonSeatCapacity` (the peon engineInput hook in packages/network/service/packs.ts) gives the openings left: the posted openings minus the candidates in an intro both sides accepted, a hire, or an intro still in flight (spec/peonCapacity.md, "Only live or successful introductions occupy an opening"); declined, expired, cancelled and no-show intros free the opening. A seat with no opening left reads `peon:openings:0` (the job_closed member rule), and `peon:seat_cap:<n>` caps the seat's slate in one run at the openings left, so a seat is never over-filled. The simulated hiring world writes seats directly and does not call these functions.
- `relay.ts`. After a mutual yes, every item one member sends the other goes through `relayItem` (`relayItemAsync` with the Clef hook in production). Only `rendered` reaches the other person, and it is empty unless the decision is pass. The relay log row has no body and no contact value. Checks: parties (the two participants, both `canBeMatched` or a pair that the network marks `teenFriendPair`, which can send moderated text only; no block, no opt-out, no hold), state (mutual and open), consent (a fresh explicit request for this item; photos need consent and owned opaque ids), text (LeakGuard, contact patterns, rating words, a minor's self-disclosure flags the age), classifier (rules, then the hook, which can only add reasons; `relayClassifierReads` decides when it reads; no hook, an error, a timeout or an answer that does not parse gives `classifier:unavailable`, and `classifierError` on the result names the cause: `no_classifier`, `unavailable`, `invalid_answer`, or the error name and code, never the text), and rate (burst, daily, photos per day, one contact share per opportunity). Any reason blocks the item, and `relaySenderNotice` gives the sender's notice (spec/relayDecision.md; owner decision 2026-11-22, D18: the hold for staff is removed). The relay reads no clock and no randomness.
- `spatialIndex.ts` and `retrieval.ts`. `SpatialIndex` indexes matchable adult members (`canBeMatched` and `ADULT_AGE`) into deterministic hex cells (`latLonToHex`, `hexGridDisk`), 168-bit weekly availability masks (`buildWeeklyAvailabilityMask`, `weeklyMaskOverlapHours`, `popcnt32`), stemmed tag postings with IDF weights, multi-facet SimHash LSH buckets, and fail-closed `Int16Array` romance age bounds (`[30000, 0]` sentinel). Below `EXACT_SCAN_THRESHOLD`, queries run an exact scan; at larger scales, the index filters by cell, time overlap, and LSH before scoring. `World` builds `spatialIndex`, `facetEmb`, `profileEmb`, `capEmb`, `desireEmb`, `intentEmb`, and `eventEmb` lazily on first use.
- `leiden.ts`. Builds an adult-only, block-free CSR graph (`buildAdultCsrGraph`) and computes deterministic Leiden community partitions at micro (`gamma = 2.5`) and meso (`gamma = 1.0`) resolutions (`detectLeidenCommunities`), incremental local dynamic updates (`updateLeidenLocalDynamic`), Burt structural-hole brokerage (`computeBurtBrokerage`), and Adamic-Adar 2-hop scores (`computeAdamicAdar`). Minors never enter the CSR graph or any brokerage or 2-hop score.
- `sinkhorn.ts`. Solves the sparse Choo-Siow quadratic-root iterative proportional fitting problem (`solveChooSiowIPFP`) on flat CSR typed arrays in O(T * |E|) time. Computes positive unmatched outside-option mass, shadow prices (`lambda_i = -2 * beta * ln(A_i)`), `p80ShadowPrice`, `medianShadowPrice`, and MIPS shadow-price vectors (`exportMipsShadowVectors`). `policy.ts` uses one shared deterministic `marketContextFor` equilibrium across `selectProposals` and `blockingPairs` so `selectionRun` keeps monotonic `greedyBound` and `blockingPairs === 0`. `packs/slop/assign.ts` uses the same solver to apply bounded congestion lifts inside `slopAssignment`.
- `status.ts`. Computes adult-only, ephemeral 6-dimensional `StatusBelief` vectors (`[phys, econ, cult, soc, warm, pot]`) with `canComputeStatus` (`ADULT_AGE` and `canBeMatched`). Combines seed-anchored `solveEigenTrust`, out-degree-normalized Jacobi-CG `solveSpringRank`, and chronological `glicko2SingleUpdate`. Cold-start priors incorporate Leiden Burt brokerage (`World.brokerage`) and `HumanVector` craft rungs, vouch quality, and extraction risk while keeping the physical dimension strictly walled inside `slop` (`physDimensionWeight`) and keeping `peon` strictly free of physical, wealth, and social-pedigree proxies (`peonCapitalAllowed`). Minors are excluded. `VERTICAL_KERNELS` and `directionalStatusMultiplier` enforce positive assortative matching, orthogonal capital parity, non-assortative exchange credits, and a warmth floor. `explorationPairAllowed` protects high-shadow-price adults from uncalibrated cold exploration unless they welcome newcomers or the prior clears the band.
- `humanVector.ts` and `packs/network/{vocabulary,taxonomy,ontology,vectors}.ts`. Compiles lazy, per-member, adult-only `HumanVector` profiles (`humanVectorOf`, `humanVectorsForWorld`) gated on `vectorEligible` (`canBeMatched` and `ADULT_AGE`). Maps 17 connection ontology types (`CONNECTION_ONTOLOGY_SPECS`), spend-comfort tiers (`spendTierCompatible`, `venueCostFitsTier`), step-ahead domain rungs (`stepAheadDeltaOk`), discretion and extraction guards (`discretionGateOk`), adult parent-support checks (`parentSupportSafe`), and single-player empty-state remedies (`classifyEmptyStateRemedy`, always `involvesOtherMembers: false`). `packs/network/vectors.ts` and `packs/friends/vectors.ts` supply exact sound `packBound` and 2-class `packClasses` (`memberMayHavePositiveVectorBonus`) so `MatchRun` keeps zero bound or class-cap violations and sub-linear search cost at scale. `packs/slop/appearance.ts` adds `photoReadinessDiagnostic`, which reads only `gate.*` and `aux.*` fields under `canRatePhotos` and `aestheticReadAllowed` and never exposes aesthetic ratings.
- `embed.ts`. Clause-scoped negation-aware local feature hashing (`localEmbed`), 4-way unrolled `cosine`, and `Float64Array` `centroid`. Negated clauses flip sign on scoped terms so negated preferences separate from positive ones without external model calls.

## Design overview: code to PRD map

| Module | What it does | PRD |
|---|---|---|
| `src/world.ts` | Canonical index over the input. **Every id goes through one alias resolver first**, covering edges, holds, feedback, interactions, facets, intents and presence. Builds embeddings, blocks, warm ties, cooldown maps, budget usage, profile revisions, clusters and inviter cohorts. Presence timeline: temporary presence overrides home, multi-home members, interval intersection. | 13.1, 33.2, ME-006, ME-011 |
| `src/filters.ts` | Hard filters. Minors policy (see below): nobody under 18 in any role, including alternates and `via`. Member level: 18+, safety hold, state/category, romance opt-in, only-when-asked / two-unanswered, interruption budget, contribution budget, per-category quota, per-category decline cooldown, reliability holdout (one forgiven no-show). Pair level: blocked/avoid either way, negative-feedback cooldown (independent of the `processed` flag), decline/expiry pair cooldown, active-duplicate guard, romance mutual opt-in plus stated preferences, stated dealbreakers. ### Research input adopted (docs/research/matching-and-graphs.md)

1. **Reciprocal value and parity.** A pair value is the integer harmonic mean of the two directed utilities minus a standing-gap penalty, and exists only when both utilities reach the lane floor and the private standing gap is inside the lane band (spec/pairValue.md, spec/matchLane.md). Groups use the lowest and the mean of their pair values.
2. **No Gale-Shapley.** Generators propose overlapping candidates, then one global constrained selection runs per tick: greedy with budgets, pair reuse, time conflicts and caps. The stable-matching blocking-pair count is logged as `runLog.blockingPairs`, as a diagnostic only.
3. **Congestion and exposure in the objective.** An in-run load penalty, plus an amortized per-member `exposureDebt` (carried debt + best viable relevance - proposals received). It is read from `EngineInput.exposureDebt` and returned in `runLog.exposureDebt` to persist. Gini, top-10% and Lorenz are reported.
4. **Warm-path value is an inverted U** in tie strength (`warmPathValue`, peak at 0.5).
5. **Off-policy logging.** Every proposal carries `selectorRank` and `selectionProbability` (1 for deterministic picks, the draw probability for exploration picks). Every scored configuration's components are logged.

Not adopted yet: OR-Tools / ILP selection, Adamic-Adar and Burt-constraint graph features, and community partitions. These are noted for v2.

## Pipeline and complexity

1. **Index.** `World` canonicalises the input. `World.match` builds profiles once per run from eligible lane memberships. It sorts each lane, side, and market block by standing and ordinal, then indexes offers, seeks, and interests in that order. Building the index takes O(N log N + T) time for N profiles and T tag occurrences.
2. **Generate.** Generators ask `searchFor(ctx, profile)`. Each search locates the standing window by binary search and visits its shortest tag postings first. If an untagged pair can reach the utility floor, the search can walk the rest of the window. It checks at most the lane's `searchBudget` pairs and visits at most eight times that many entries. The result is Exact when no unchecked candidate can enter the kept list. A Budgeted result gives an `unseenBound` for any candidate it may have missed; a search whose walk is spent closes as soon as no touched candidate can still enter. A pack can give `PackVectors.masks` (bitsets that the one pair gate and the touch test the same way, a superset of the pack rules), `PackVectors.packBound` (an upper bound on its pack value, used in place of 1000 in a touched bound) and `PackVectors.packClasses` (a whole-number class for each membership and a class cap; the index keeps the classes of each segment, and the untouched bound counts the searcher's pack term at the largest cap over the classes of the reached segments, with `untouched` true only after every tag range is walked). A pack value is a whole number from 0 to 1000 for the direction from `a` to `b`. A trait list has one whole number for each entry of `costs`. A membership without a segment reaches every partner, and every partner reaches it. A profile's ordinal is its position in the entity-id order of its block. The index sorts a block by segment (profiles without a segment first), standing and ordinal, so each segment is one range of positions, and each tag posting holds ascending positions. `buildProfiles` returns the profiles in canonical order (block key, then entity id). A member who cannot be matched (minor or unknown age, under the pack or config age floor, safety hold, paused, not opted in to the lane's category) gets no profile, and the pack is not asked about a member who fails the core checks; members whose pack returns the same partner-segment list share one set. `bruteForceCandidates` is the oracle for the simulator gates only: the same pair function over the whole partner block, with no pruning. `mutualEdges` gives one edge for each pair that either side kept, because the pair value is symmetric. One `MatchRun` keeps a `PairMemo`: the other side's search reuses a checked pair value or refusal, and the reuse still counts as one check, so pack pair rules must be symmetric. Without a pack value, the touched bound is the pair arithmetic and the check adds only the pair gate. Circles use the search edges (`World.match.circles(lane)`). [Candidate search spec](../../spec/candidateSearch.md)
3. **Screen.** The generated candidateScreening order over every generator candidate (exploration, warm paths, groups, events). In the Pairs phase a candidate with two or more participants must name a lane (`no_lane`) and every pair the lane requires must have a pair value from the one pair gate (`no_pair_value`); an alternate without a pair value with each primary it pairs with is dropped (`screenCandidate` returns the kept alternates). The generic activity planner (`plans.ts`) uses the same pair gate on each pair in its bounded availability pool before making circles or partner plans.
4. **Score.** Pair values for fit and mutual benefit plus the cost terms (timing, activation, interruption, load, repetition, social risk) and confidence.
5. **Judge, select, emit.** The judge can only lower scores or remove candidates. `runLog.search` reports searches, pair checks, index entries visited, exact, budgeted and empty results, and the largest unseen bound (-1 when every result is exact). It also counts touched candidates bounded (`bounds`), checks made when no touched candidate could still enter (`checksAfterSettled`), checks above the bound used (`boundViolations`), pack values above the pack bound (`packBoundViolations`) and pack values above the class cap of the partner's class (`classCapViolations`, with the untouched cap also when the pair shares no tag), all four required to be 0, budgeted closes by cause (`touchClosed`, `checkClosed`), reused pair values (`memoHits`), and refusals by reason (`refusals`: the gate's reason or `below_floor` at a check, `mask_refused` at a touch).

## Minors policy (PRD 17.4, as amended by the founder decision of 2026-10-05)

Changed (owner decision 2026-11-22, answers A2 to A5): friends.help and the Friend lane of The Network
can introduce a person aged 13 to 17 for friendship.

- The rule is `groupAgeAllowed` in [spec/friendIntroAge.md](../../spec/friendIntroAge.md).
- It applies only when `EngineInput.teenIntros` is true. The network sets it while staff have not stopped teen introductions.
- It applies only in the friends.help categories `social` and `hobby` and the ntwrk category `social` (`teenFriendCategory` in [spec/matchLane.md](../../spec/matchLane.md)).
- It applies only to members that the network marks `teenReady`.
- Each other person in the roster is aged 13 to 18 and is teen ready. The birth date of each other person is at most 2 calendar years from the birth date of the minor.
- `World.minDay` and `World.maxDay` are the earliest and the latest civil date at `input.now`.
- The pack declares the lanes with `LaneDef.minors`. `validatePack` refuses `"teenFriendship"` outside those categories.
- `candidateAgeReason` also needs a teen generator (`teenGenerator`). These are ntwrk `intent_to_capability` and `group_composer`, friends `friend_circle` and `activity_partner`, member requests and friends plans.
- `candidateAgeReason` also needs the shape of a friendship meeting (`teenIntroShape`). Every person has a teen role, the meeting is one-to-one or a small group, there is no `via` and no event anchor.
- A roster with a minor has at most 6 people (`teenRosterSizeAllowed`).
- A roster with a minor that has no generator, format or roles fails `candidateAgeReason`.
- Before the screen, the engine gives each alternate of a roster with a minor the role `guest` (small group) or `peer` (one to one). A proposal with a minor carries its `format`.
- A teen roster gets no warm tie. Its probe has no shareable attribute and no area, and its explanation has no facet text.
- `buildProbe` refuses a teen roster unless the spec names the generator, the format and the roles.
- On friends.help only, the weekly planner builds small teen groups: tables, activity partners, repeats and crews.
- The roster of each teen group passes `teenGroupReason` (the rule, the size and `teenGroupPlanApp`).
- A teen group meets for an activity and at a place marked all ages (`activityAllAges`, `venueAllAges`, `teenPlaceAllowed`). `teenPlanReason` reads the age marks of the plan venue from the venue list of the caller (`VenueAges`, by `venueId`) at each check. A teen plan with no `venueId`, or with a venue that the list does not have, is refused. Thus a stored plan uses the current marks of its venue.
- A teen group meets from 10:00 to 19:00 in the time zone of the plan city (`teenPlanWindowAllowed`), with no host.
- `teenPlanReason` is the one plan check. It checks the roster, the activity, the place marks, the times and the host. The planner calls it when it makes a plan, and `buildPlanProbe` calls it again at send time.
- `buildPlanProbe` gives a teen plan the tag-only form: the activity, the time, the public place and the borough.
- Adult plans never use an entry marked `adultPlans: false`.
- `same_table_again` and the ntwrk planner stay adults only.
- `candidateAgeReason` and `buildProbe` read the age rule on the latest civil date of the end of the meeting window, or of `input.now` if it is later. Thus a partner who turns 19 before the meeting is refused.
- An attention item of a minor passes the minor gate only when the network sets `teenFriendAllowed` and the item names its other members.
- The relay guard accepts only moderated text for a pair that the network marks `teenFriendPair`. It blocks on the `teen:` codes and on every off-platform move, and it uses `RELAY_LIMITS.teenDaily`.
- In a teen pair, the relay guard blocks on `teen:adult_age` when the sender states an age of 19 or more, or a birth year that can give 19 or more on the latest civil date.
- In a teen pair, the relay guard blocks the own age words of a minor sender with `teen:age_talk` in place of `minor:signal`.
- A relayed text passes only after a classifier reads it cleanly, for a teen pair and for adults. Without a classifier the text gets `classifier:unavailable` (owner decision 2026-11-22, D18).
- In a teen pair, the classifier also reads a text that has reasons that are not final. Any reason blocks, so a teen-pair text passes only after a clean read.

When `teenIntros` is absent or false, the table below is the full policy.

The slop onboarding question `slop_age` stays an age question. The network join step asks for the
birthday and stores the birth date (spec/textEnrollment.md). The slop loop starts from that age and asks
`slop_age` only when the member record has no age, and the slop extractor stores an age, not a birth
