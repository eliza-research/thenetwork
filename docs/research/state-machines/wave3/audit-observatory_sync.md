## 1. suspected_defect (new)

### D1 (P1). The reveal badge ignores a grant that the server holds but this tab did not make. PII shows with no badge and no End button.
- Where: web/store.ts:600-611 (loadReveals runs only at land and after a POST/DELETE answer), panels.tsx:229-231 (MemberPanel fetches member detail; the server decides the reveal), panels.tsx:547-548 (RevealControl reads only `s.revealFor(id)`), src/server.ts:422-424, 498-505 (`/api/member/:id` uses the server grant of the staff user and sets `d.revealed = { until }`; no client code reads `revealed`), server.ts:307-310 (grants are per staff user, mode, app and member, not per tab).
- Trigger: one staff user (same token or SSO identity) has tab 1 and tab 2 open on app A in real mode. Tab 1 lands; its GET /api/reveal answers [] (list known, badge off). In tab 2 the user reveals member X (grant made). In tab 1 the user opens member X: `/api/member/X` returns the revealed detail (names, own words) because `revealFor(u, A, X)` finds the grant. Tab 1 shows the PII, RevealControl shows the "Reveal" button, not the "Revealed" badge and not "End". Nothing re-reads the list until the next load.
- Rule broken: badgeFollowsGrant ("while the server holds a grant for a member on screen and the reveal list is loaded, the badge shows", B10, admin-console 4.4). The model cannot reach it: it has one tab, and `rv.server` only changes by this tab's grant/unreveal/expire (observatory_sync.qnt:427-480).
- The same fix closes the open carve-outs `stale` and `failed` (section 2).
- Fix (in scope: security, B10 family): when a member detail (or timeline, or app panel) answer carries `revealed` and `revealFor(id)` has no grant, call `store.loadReveals()` (or show the badge from `revealed.until`). Model: add an `otherTab` environment action that sets `rv.server` with no change to `rv.badge`, and a `detailAnswer` action that applies the new rule; state `badgeFollowsGrant` without the `not(rv.stale)` guard for members whose detail is on screen. A tests/e2e case: two clients on one token, reveal in one, read member in the other, check the badge input.

### D2 (P2). An app switch keeps the old app's `env` (banner, database, capabilities) and `clock`. B9 residual.
- Where: web/store.ts:401-405 clearData empties members, edges, opps, feed, stats, runs, game, truth, network, requests, reveals, but not `env` or `clock`; only applyFull (store.ts:390) replaces them. main.tsx:79-86 builds the banner from `env.app`, `env.label`, `env.database`, `env.piiRevealed`. `canAct`, `canWrite`, `realOnly`, `showReviewTab` (store.ts:599, 836-843) and RevealControl (panels.tsx:546, `env.piiRevealed`, `env.capabilities.hiddenTruth`) read `env`.
- Trigger: real mode, app A loaded (env.app = "A", env.database = A's database). setApp("B"); `/api/state?app=B` fails (B's source cannot start, server.ts:226-247 throws, 500). The switcher says B, the panels are empty, and the banner says "A · PROD · read-only" with A's database in the title. The controls follow A's capabilities. The same holds during every normal switch until B's state lands.
- Rule broken: "nothing on screen belongs to another app" (B1/B9; J6 in frontend-observatory-state.md). The model's `good` cannot see it: switchApp clears the ghost `screenApp` for all panels (observatory_sync.qnt:283-288), which is stronger than clearData.
- Fix (in scope, reproduced-bug class): clearData sets `env = undefined` and `clock = undefined` (banner() already handles `!env`). Model: split `screenApp` into `dataApp` and `envApp`, set `envApp` only at land, and add `envApp == "" or envApp == ui.sync.app` to `good`; it fails today.

### D3 (P2). DELETE /api/reveal ends the grant before the audit write; on an audit failure it answers 503, so the revoke has no audit row and the client keeps the badge.
- Where: src/server.ts:596-603 (`reveals.delete` at 599, then `record` at 600, `if (no) return no` returns the 503 from server.ts:416-418). POST does it in the right order (record at 590, set at 592).
- Trigger: the audit sink is down (Postgres audit unavailable). Staff press End: the grant is deleted, no `reveal_revoke` row is written, the answer is 503 "request refused". The client (store.ts:619-622) keeps the badge and shows "audit log unavailable: request refused", which is false.
- Effect: an access change with no audit row; a wrong badge (safe direction). The model has the opposite assumption (section 3, E3).
- Fix: record first, then delete (and on failure keep the grant), or delete and answer 200 with a logged audit failure. Integration case in packages/observatory/test/staff.test.ts with a failing audit sink.

### D4 (P2, devtool: sources/game.ts is "na" in the ledger). A game reset can publish a non-reset delta from the new world.
- Where: sources/game.ts:686-697 (`await this.init()` then `this.pendingReset = true`), init swaps the store at game.ts:172 and then awaits `this.world.begin()` at game.ts:241; push() at game.ts:436-444 adds `reset` only when `pendingReset` is set. Other control paths call `this.push()` (game.ts:200 takeover callback, 577, 584, 710, 718, 752, 784, 799) with no lock against a running reset.
- Trigger: staff 1 sends `reset`. While init awaits `world.begin()`, staff 2 sends `review` for an old opp id: game.ts:710 `this.push()` on the new store emits version 1 (new members) with no reset. A client synced at old version 1 treats it as "meta" (clock, game, network of the new world on old data); at old version 0 as "data" (new-world members merged into old-world maps, feed items with restarted seq dropped by appendNew). The next timer push carries the reset and the client reloads, so the window is short.
- Fix: set `pendingReset = true` before `await this.init()`. Model: section 4, G2 (server epoch).

### D5 (P2, dev/staging only: production is real-only). The reveal GET is tagged with the app but not with the mode, and a mode switch does not clear the reveal list.
- Where: store.ts:601-603 (`const app = this.app, gen = this.revealGen`; only `app !== this.app` is checked), store.ts:479 and 494-503 (mode change: picks, focus, load; no clearData, no revealGen bump), server.ts:576 (GET filters by the server mode at handling time).
- Trigger: real mode with a live grant for X; switch to game, back to real. The GET sent in game mode is slow; the real-mode GET answers [X]; then the game-mode GET answers [] with the same revealGen: revealMerge is true, the list becomes [], and the badge for X goes while the real grant is live (badgeFollowsGrant). Also, between the mode message and the next GET answer, the old mode's grants stay in the list.
- Fix: capture `this.mode` with the app in loadReveals, or bump `revealGen` on every mode change and in clearData.

## 3. model_error

- E1 (P1, ledger). docs/formal-coverage.md:260 and drift.json map `packages/network/src/store.ts` (the Postgres network state store, no relation to this model) to observatory_sync. The file the model copies is `packages/observatory/src/store.ts` (pushFeed :104-109, snapshot :158-164, takeDelta :171-187: version bump only on change, reset on removed edges). Its row (formal-coverage.md:343) says "na, no decision" and names only staff_console. Also not mapped: sources/game.ts (:337, "devtool na"; pendingReset and the new Store per reset are in serverReset's comment), sources/real.ts push, main.tsx:285-286 (the filter bar dim that tabNonInterference is about), panels.tsx:541-549 (RevealControl, the badge itself), web/logic/views.ts effectiveTab (shownTab picks the tab the bar dims by). A change to takeDelta (for example a version bump on every clock tick) would not fail the drift check for this model.
- E2 (P2). `good` checks a ghost `screenApp` that switchApp clears for all panels at once (qnt:283-288). The code clears only part of the per-app state (store.ts:401-405 keeps `env`, `clock`). The invariant is stronger in the model than in the code, so it passes for env in vain (D2).
- E3 (P2). `serverEnded(status)` says only 200 and 404 end the grant (qnt:122). The server deletes the grant before the audit write and answers 503 when the write fails (server.ts:599-601, 416-418). So a 503 ends the grant. Safe direction (badge on, no grant), but the model states the opposite of the code. A 403 after role removal (guard ["safety"], server.ts:603) leaves a grant that `revealFor` will refuse (server.ts:424); also safe direction.
- E4 (P2). `tabNonInterference`, `safetyIgnoresOrigin`, `reviewIgnoresRange` evaluate a hand-written `shellKeys` (qnt:182-190). For review and feed it is defined as `tabKeys`, so the check cannot fail there; for the others it is a constant subset fact over 6 rows. It does not read the code and does not see a new filter call site. It also ignores `drawerOpen` (main.tsx:286 dims only when the drawer is open) and that the bar dims by `shownTab` (effectiveTab), not by `ui.drawer`. Proposal: replace with a sim gate or LemmaScript extraction that lists the keys used per tab body, or keep it and add a grep check in the formal block.
- E5 (P2). `appendNewSorted` (qnt:604-605) follows from appendNew by construction; it checks order and no repeat, but not loss. The B18 rule and LemmaScript `appendNew` (inclusion ensures) also say no item goes missing. Add `feedContiguous`: when `ui.screenApp != ""`, the feed seqs are exactly 1..len. In the current bounds it should hold (a state at V holds 1..s, delta V+1 carries sent+1..hi with sent <= s). It would fail with G2 (seq restart) and is the right form for the B7 risk.
- E6 (P2). `grant`, `unreveal` and `otherAnswer` are atomic: the request and its answer are one step, under the current app (qnt:427-472). In code, reveal() and unreveal() answers apply to `this.reveals` with no app or mode check (store.ts:614-635), after any number of switches. With real-mode member ids unique (network.members.id is the primary key), this has no visible effect today, but the model cannot show it. Split each into send and answer actions that carry the app.
- E7 (P3, comment). qnt:309 says "The constructor calls connect() and load()". The constructor (store.ts:273-275) does not; main.tsx:35 does, in a React effect, load first.
- E8 (P2). Single tab: the server grant is per staff user (server.ts:310); the model makes `rv.server` change only by this tab. This is why D1 is out of reach (see D1 for the action to add).

## 5. What the model gets right (checked)

deltaMove, step, admits, owns, appendNew, revealMerge, revealReread, unrevealStep, tabKeys, passes, visible: same decisions, same order as sync.ts and filters.ts. applyMsg matches applyDelta (buffer, reload via load, drop, meta and data both call step). landAnswer matches load (admits, applyFull, land, replay of a local copy of the buffer, with a reload inside the replay starting a new buffer). failAnswer matches the catch path. switchApp matches the setter plus setApp. The server actions match pushFeed (no version change), takeDelta (version only on change; reset with removed edges uses up the new feed), the game reset at the same version, and the clock-only "clock" message (no version, not modeled, harmless). The reveal GET is sent only at an admitted land and after a POST with no grant, as in code.
