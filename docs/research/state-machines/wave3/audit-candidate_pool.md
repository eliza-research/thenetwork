## model_error

1. **romance groups are allowed in the model (invariant weaker than the rule).** packs/network/rules.ts:84 `romance_group`: romance is pairs only. composeGroup in the model (candidate_pool.qnt:275-311) accepts lane "romance" with 3-4 members and only flags `groupRomanceOneSided`. The code refuses any romance configuration with participants != 2 in candidateReason (filters.ts:170-173 pre-rules). Fix: add `groupRomance: lane=="romance"` flag to composeGroup and to `romanceMutualOptIn`, with the pre-rule as a guard. The code obeys it, so safety would still hold.
2. **romanceScoredOneSided in scorePair cannot fail.** candidate_pool.qnt:263: `romanceSat(anchor,b) and not(optIn(anchor) and optIn(b))`; romanceSat (line 152) for network is exactly `optIn(x) and optIn(y)`, for friends false. The flag is `X and not X`. It only catches a mutation of the model's own romanceSat, never a trace. The code gate (complementarity.ts:63-67 romanceMutual) also checks orientation, age range and `romance` prefs present; the model drops these as "can only remove", which is right, but then the flag tests nothing. Fix: give romanceSat an oracle input (an ontology may return true) and flag scored-without-opt-in; or document it as a transcription check.
3. **partner plans have alternates in code; the model forbids them.** plans.ts:353 `alternates.length >= (partner ? 1 : pcfg.alternates)`: a partner plan from planProposals carries up to 1 alternate. Model newPlan (line 445) requires `alts == Set()` when `partner`. finish() does not fill partner seats (planner.ts:215), so the alternate stays on the plan and run() (planner.ts:408) keeps it. Effect on invariants: none known; the model is narrower than the code.
4. **run() alternates are not added to `used`; the model adds them.** planner.ts:407 adds only `fp.invited` to `used` (tables() at 389 adds invited and alternates). Model newPlan (line 452) adds `g = primary ∪ alts` for every new plan, so `planSeatTwice` is stronger than the code for run() plans. See suspected_defect 3 (not reproduced).
5. **partnerPlan assumes a presence check the code does not do.** Model partnerPlan (line 467) requires `city(x) == city(y)` and the header says activityPartner candidates "passed candidateReason (... presence overlap)". planner.ts:451-475 uses `activityPartner` output directly (generators.ts:96-127): memberReason, pairReason and transit only; no candidateReason, no w.overlap / canMeet, a fixed `preferredCity: "nyc"`. The model also adds no coLocated flag for partner plans, so nothing checks it. Fix: drop the city guard and add a `partnerApart` flag outside safety (or accept, since friends is NYC-only and local only).
6. **viaCandidates is wider than twoHop in a way that hides a liveness gap.** retrieval.ts:39-55 picks ONE via per target (the strongest), skips direct neighbours (`direct.has(b)`), and does not skip a minor or blocked via. The model lets `intro` pick any via. In the code a minor or blocked strongest via drops the whole warm candidate (generators.ts:298 `isMinor(w, path.via)` -> continue; filters.ts:183 -> "blocked") although another adult via exists. Not a safety issue (only removes), but the model cannot show the lost warm path.
7. **Most safety flags are guarded by the same predicate (they test the transcription only).** introMinor/introBlocked/introViaUnsafe/introApart (lines 225-245), groupBlocked/groupSizeBad/groupApart/groupAltBlockedWithPrimary (285-300), planBlocked/planSizeBad (444-456), partnerBlocked/partnerOverCap (467-474): each guard excludes the flagged case. They fail only under a guard mutant. That is the pattern quint/README allows, but the report should not count them as code checks. The flags that can fail on a trace are those of the planner passes outside safety and `submittedBlocked` / `altPairBlockedEngine`.

## model_gap

1. **Pass 1 host from the unfiltered hostRotation** (planner.ts:249): `crewSessionPlan({ ...crew, members }, ...)` keeps the original `crew.hostRotation`, and plans.ts:719 picks `hostId = hostRotation[sessions % len]`. network.ts:3490 filters hostRotation by the eligible members; the planner does not. Not modelled (no host in Crew). Adding `hostId ∈ invited` as an invariant would fail. See suspected_defect 1.
2. **ConsentNetwork crew sessions use minMembers (3), the planner uses 2.** network.ts:3489 `members.length < this.pcfg.crews.minMembers` vs planner.ts:247 `< 2`. The model treats sessionSizeOk as "can be intended"; the two code paths disagree, so it is a real inconsistency (see open_carveout 6).
3. **Composer forced members** (group.ts:81-102): forced ids skip evaluateGroup when there is one (city = preferredCity or homeCity) and are not memberReason-checked in composeGroup. shared_intent_pooling checks the seed before (generators.ts:171). Not modelled; adding it would not break an invariant because candidateReason re-checks participants.
4. **Alternates are never memberReason-checked.** group.ts:137-147 checks compat and overlap only; filters.ts:175 checks only minors for alternates; network.ts:4271-4286 distinctAlternates checks minors, blocks and first names, not holds, pause or opt-out. Within one engine run the pool is from eligibleMembers so this is safe; a hold placed after the proposal is caught at backfill by filters.ts:231 sendTimeReason. The model has no `held` flag for alternates and no backfill step, so it cannot show this. Adding `groupAltHeld` at composeGroup time would fail on traces where setHold interleaves retrieve and composeGroup (the code never interleaves within one run); the right extension is a backfill action with sendTimeReason.
5. **requireCity / preferredCity** (group.ts:62-64, 141-142; filters.ts:207-209): a member can be in several cities at once (geo.ts:22-28 undated routine presence adds a city). The model has one city per member. Only removes; no invariant change.
6. **Network group_size pre-rule** (packs/network/rules.ts:76-81) applies only to kinds group/newcomer_welcome; eventAnchor groups (generators.ts:257, kind event_coattend) rely on composeGroup's own minSize/maxSize (maxSize min(4, cfg)). The model applies MIN_G..MAX_G to every composeGroup. No break; worth a comment.
7. **Pass 2 hostRotation of c2** (planner.ts:272) and **venue/transit and time options** are oracles; finish() quorum checks are in the model. OK.
8. **Pass 5 does not read `taken` or `used`** (planner.ts:456) — consistent with the model (partnerPlan reads neither); a member can get a crew session, a new table and a partner plan in one week. The probe shows 569-640 cross-kind duplicates per seed. Design choice (spreadNew=false), not an invariant.
9. **Repeat pass skip instead of trim** (planner.ts:288): one blocked pair among ids drops the whole outcome. Liveness only; model matches (guard pairwiseOk on ids).
10. **detectCrews order and minPlans=2 branch** (plans.ts:662-689): the model has minPlans 1 only (FRIENDS_PLANS.crews.minPlans 1). OK for the default.
11. **The final alternates filter** (planner.ts:478) is not modelled; it only removes.
12. **No crash, retry or timer paths**: the planner and the composer are pure functions over one World snapshot; there is nothing to crash mid-way. Correct to leave out.

6. **sessionSizeOk** (planner.ts:247). The probe reaches it (12 two-person crew sessions in seeds 6 and 8). network.ts:3489 uses minMembers 3 for the same thing. Needs a maintainer decision (intended or not); if not intended, use `pcfg.crews.minMembers`.

## suspected_defect

1. **Crew session names an ineligible host (planner.ts:249 with plans.ts:719).** Trigger: crew {a, b, c, d} with hostRotation [a] (a has the host tag). a states age 16 (or gets a safety hold). Next week planFriendsWeek: members = [b, c, d] (eligible), crewSessionPlan({...crew, members}) keeps hostRotation [a], so `hostId = a`. The plan's hostId names a minor/held member who is not invited. plans.ts:421 gives roles only to invited ids, so a is not contacted; but any copy or capital code that reads hostId (network.ts:3505 withReach reads `plan.hostId` for organizing reach, in the ConsentNetwork path, which filters; the sim planner path does not) would act on a. Severity P2 (sim only); fix: filter hostRotation as network.ts:3490 does.
2. **Two-person crew sessions in the planner, three in the ConsentNetwork** (planner.ts:247 vs network.ts:3489). Reproduced by the probe (seeds 6 and 8). Already a carve-out (sessionSizeOk); listed here because the two code paths disagree.
3. **run() alternates are not reserved (planner.ts:407-408)** — NOT reproduced. Path: run(zone z1) gives plan P1 with alternate x (x not added to `used`); a later run() or tables() call may make x an alternate of P2 too; planner.ts:478 removes x only when x is INVITED elsewhere. With openTable (packMatcher.ts:86) both alternate lists are probed at once. The probe saw 0 such members in 1,249 plans (seeds 5-8), probably because tables() runs first and reserves most members. Keep as plausible; the model hides it by adding alternates to `used` (model_error 4).
