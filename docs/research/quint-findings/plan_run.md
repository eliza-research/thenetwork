# Quint findings: `quint/plan_run.qnt`

Module plan: [2026-11-07-state-machines.md](../2026-11-07-state-machines.md) section 6.7 (P0). Machines: M-045
`plan-run`, M-046 `plan-fallback`, M-124 `crew-offer-and-crew`. The first model followed the code at `ad67275`
and reproduced the register defects. The model now follows the FIXED code on branch `wave2/plan_run` (the fix
commits `e359245` to `a2f1a1e`, and the Q-plan_run-2 fix that comes with this update). This file is
hand-written. The traces are generated by the Quint simulator and shortened by hand.

Since the update for bounded model checking (section 6), the crew machine (M-124) is its own model,
[`quint/plan_crew.qnt`](../../../quint/plan_crew.qnt) (findings: [plan_crew.md](plan_crew.md)). The plan run and
the crew share no state; the crew reads only STOP, the trust watch, the minors policy and the clock, and
`plan_crew.qnt` has those events too. The SD-144 and SD-444 rows below are checked there.

## 1. Final state

`bun run quint:check --verify quint/plan_run.qnt quint/plan_crew.qnt` passes: typecheck, the run tests,
`safety`, all witnesses, and `verify safety` (Apalache) for both models.

- `plan_run.qnt`: 14 run tests, `safety` with 13 invariants, 7 witnesses, `verify-steps=2` from the initial
  state and from three checkpoints (section 6).
- `plan_crew.qnt`: 3 run tests, `safety` with 3 invariants (`sessionSlotOnce`, `handoffCountsSessions`,
  `crewOptedIn`), 3 witnesses, `verify-steps=12`.

Together they have every invariant, witness and run test of the combined model before the split. The
invariants of the two skipped defects are out of `safety`: `revealSymmetric` (SD-479) is `skippedDefects` in
`plan_run.qnt`, and `crewEndHeard` (the notice part of SD-444) is `skippedDefects` in `plan_crew.qnt`. Each has
a comment that gives the defect id and the reason. They still fail: the random simulation finds a violation of
each, and the run tests `sd479LateJoinTest` and `crewHandoffTest` show it.

## 2. What the model contains

- **Code.** `packages/engine/src/plans.ts` (startPlanRun, recordPlanAnswer, checkPlanDeadline, planFallback)
  and `packages/network/src/network.ts` (beginPlan, planLane, planProbe, planDeadline, planAnswer, planAct,
  bookPlan, planReveal, planJoin, planFallback, planOut, dropMember, handleDrop, close, the `plan_probe` and
  `reveal` send hooks, checkRecipient, busy, bookedNear, applyBlock, and the intro `reveal`). The crew code
  (crewOptIn, crewSessionPlan, crewSessions, resolveCrew, onCrewAnswer) is in `plan_crew.qnt`.
- **Actions.** One inbound message, one tick, one review decision or one actor event is one unit. `probe` is
  its own action because the send window, one-a-day and the allowance only defer a plan probe. Actor events:
  STOP, trust watch, minor signal, block, "can't make it", an intro for a plan member (probe, yes, book).
- **Oracles.** The probe copy leak gate, the send-time leak guard, the Blooio streak (`canSendLogistics`) and
  "a matching public event exists".
- **Bounds.** Members a-e. One group plan: invited a, b, c, d; bench e; quorum 3 or 4 (chosen at init; 4 is
  the trace of the SD-480 integration test); `groupSize[0]` 2 or 3. Hours are small integers: deadline 4,
  late-join cutoff 7, start 10, probe silence 3. The partner plan that the fallback submits is recorded
  (`partnerAsked`), not run: it is a new opportunity with its own review. The crew (a, b, c, weekly slots 0-4)
  is in `plan_crew.qnt`.
- **Steps of one unit.** bookPlan and planFallback are their own actions (`finishBook`, `finishFallback`). The
  unit that needs them (an answer, a tick, a probe, an actor event) writes the request into `todo`. While
  `todo` is not empty, only these two actions are enabled, so no other actor runs inside a unit, as in the code
  (one handler, no await). What the unit does after them is in `todo` too: the answer that waited for the
  deadline step (`ansM`, `ansYes`), and the silent members of a tick after a smaller booking (`late`). The
  oracles of the unit (the Blooio streak, "a matching public event exists") are kept in `todo`. The invariants
  and witnesses are read only between two units (`idle`).

## 3. Changes to the model

| Action or helper | Change (follows the fixed code) | Defect |
| --- | --- | --- |
| `bookPlanCore` | `enough` needs 3 seated (quorum, or 3+ for an activity whose smallest group is 2). The members left out (plan_conflict, refused seat) get the note, except minors and members on watch. | SD-008, SD-480 |
| `planFallbackF` | Two yes-sayers: the plan closes, a partner plan is submitted, and the two get the note. Three or more: the smaller group is booked as before. | SD-008, Q-plan_run-2 |
| `handleDrop` | The plan stays on only with 3 or more yes. | SD-078 |
| `planAct` (backfill) | The alternate is added to `plan.invited`. | SD-204 |
| `probeF` | `about` is the participants whose status is not no, unavailable or dropped. | SD-046 |
| `planDeadlineF`, `answer`, `tickF` | One deadline step. An answer runs it first; if the plan closes there, the answer is not counted, there is no ack, and a yes gets the note. | SD-423 |
| `introBook` | A member booked in the plan at that time is left out of the intro. | SD-268 |
| `planAnswerF` | A "late" yes (after the late-join cutoff) is unavailable and gets the note. | Q-plan_run-1 |
| `crewTick` | The hand-off runs before a proposal and counts held sessions only. The dedupe is on the plan id (crew and slot). | SD-444 (counting), SD-144 |

Invariant changes (none is weaker than before):

- `noNameBeforeQuorum` read the historical `named` set against the current answers, so a member who was named
  in a correct reveal and then said "can't make it" made it fail. That was a model error. The check now runs at
  each reveal (`earlyName`): no reveal names anyone before 3 or more yes-sayers are seated.
- `pairNeverBookedFromGroup` uses the group minimum 3, not the quorum, because the fallback books a smaller
  group of 3 when the quorum is 4. `groupNeverShrinksToPair` is now stronger: a scheduled plan always has 3 or
  more yes.
- New: `partnerPlanNotBooked` (the pair of a group plan that fell to two is never seated; the plan is closed).
- New witnesses: `witness_partnerPlan`, `witness_crewHandedOff`, `witness_leftOutTold`.
- The crew session end now picks the open session (the last proposal) in `step`, so that the hand-off is
  reachable in random traces.

Changes for bounded model checking (section 6). None of them changes a trace of the code that the model has;
the run tests replay the same traces with the same results:

- The crew machine moved to `plan_crew.qnt` (no shared state).
- `todo`, `finishBook` and `finishFallback` (section 2). Before, bookPlan was inlined about ten times in the
  transition relation (each answer, probe, tick and actor event can fall back, and a fallback can book).
- The maps `answers`, `status`, `sentAt` are total over the members ("" or -1 is "no entry"), and the set of
  messages is replaced by the facts that the invariants read (`sent`, `minorMsg`, `blockedMsg`, `optedOutMsg`,
  `eventMsg`). `named: Set[(str, str)]` is `knows: str -> Set[str]`.
- The tick's silence fold stops at the member whose silence makes the run fall back. In the code, the later
  members are then not recorded (the run is closed), or, when the fallback books a smaller group, recorded as no
  with no other effect; `finishBook` does the second case (`lateSilence`). New run test: `silenceFallbackTest`.
- The step weights are guards on one `pick` value (the simulator draws the nondet values again when the step is
  disabled), not copies of the same action.
- `init` can start at the initial state or at one of three checkpoints (section 6). The witnesses ask for
  `fromStart`, so each witness state is reached by the model's actions from the initial state, as before.

## 6. Bounded model checking

`bun run quint:check --verify` passes for both models (Apalache 0.62.4, the default server with a 4 GB heap).
Before this update, Apalache did not finish even one step of the combined model: with a 10 GB heap, the
`tick` transition (which inlined bookPlan and planFallback through the silence fold) ran for 8 minutes at
15 GB resident memory with no result.

What made it possible (section 3 lists the changes):

1. The crew is its own model.
2. bookPlan and planFallback are each once in the transition relation (`finishBook`, `finishFallback`).
3. Total maps over the members, no set of messages, no set of name pairs.
4. One action per branch of `step` (weights are guards on `pick`).
5. `init` starts at the initial state or at a checkpoint.

The checkpoints are states that the actions reach from the initial state. The run tests `cpTwoYesTest` and
`cpBookedTest` replay the actions and compare the whole state:

| Checkpoint | State | Quorum and group size |
|---|---|---|
| 0 | the initial state (in review) | quorum 3 or 4, smallest group 2 or 3 |
| 1 `CP_TWO_YES` | a, b, c, d got the probe at hour 0; a and b said yes | the same four choices |
| 2 `CP_BOOKED` | then c said yes: a, b, c are booked and named to each other, d is pending | quorum 3, group size 2 or 3 |
| 3 `CP_TWO_YES` at the probe deadline (hour 4, after four clock steps) | the same four choices |

With `verify-steps=2`, Apalache checks every trace of two steps from each of these states:

- From 0: the review decision, the first probe, STOP and the other actor events in review and after approval.
- From 1: a third yes and bookPlan (quorum 3 books; with quorum 4 it waits), a no and the backfill of e, STOP,
  trust watch, a block or a minor signal during the probe, and these events after bookPlan.
- From 2: the late join of d, "can't make it" (the group falls to two and closes), STOP, watch, minor signal or
  a block in a booked plan, and the tick.
- From 3: the answer that runs the deadline step first (SD-423), and the tick at the deadline with planFallback:
  the partner plan for the pair, the solo event or next week. The smaller-group booking after the fallback is
  one step more (tick, planFallback, bookPlan); the run tests and the simulation cover it.

Measured on this machine (load average 40 to 90 from other sessions; times are wall clock):

| Run | Result | Time |
|---|---|---|
| `quint verify --max-steps 1`, combined model before this update, 10 GB heap | did not finish (step 1, `tick`) | stopped after 8 min |
| `--max-steps 2`, plan model with `todo`, initial state only | no violation | 26 s |
| `--max-steps 3`, the same | no violation | 2 min 25 s |

| `--max-steps 2`, with the checkpoints (the model's `verify-steps`) | no violation | 2 min 41 s |

the hand-off, is 10 steps. Apalache finds `witness_crewHandedOff` (a violation of the witness) at 16 steps in
3 s.

What Apalache does not check: traces longer than two steps from a checkpoint. Those are covered by the random
simulation (50000 traces of 40 steps from the initial state and the checkpoints, and the safety runs at three
more seeds) and by the run tests.

## 7. Model choices that matter for the results

- Between two units only: `safety`, `guards`, `skippedDefects` and the witnesses are read when `todo` is empty.
  Inside a unit, the plan can be half done (for example, a run that is closed before planFallback ran).

- `yesSayerTold` exempts members who left on their own or by policy, and a plan closed for the minors policy
  or a block. Code comments (dropMember, applyBlock) say that any later message about such a plan is a minor
  contact or says why, so silence there is by design. bookPlan's note also skips minors and members on watch.
- A yes after the probe deadline gets no ack (the code returns before it), so it is not in `promised`; it still
  gets the note.
- `probe` is enabled only while probing before the deadline, or while booked until the cutoff.
- An open intro (probing, yes or booked) makes the member busy for plan probes, as `busy()` does.
- When the fallback has three yes-sayers but one of them is left out again (plan_conflict), the plan closes and
  all three get the note; the two others get no partner plan, because the engine counts three yes-sayers
  (`sd480PairLeftTest`). This follows the code.
