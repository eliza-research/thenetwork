# Judge v2: soft labels, fixed prompts, dev/test split (2026-10-07)

Follow-up to `2026-10-06-judge-passes.md` and `2026-10-06-luna-error-analysis.md`. This work implements the analysis's recommendations 1 (labels) and 3/5 (prompts), re-runs every pass with gpt-6-luna, and reports on a held-out test split.

> Hand-written: everything except the tables marked "generated". Generated tables come from `packages/evals/src/judgeV2.ts` (`runs/evals/results/judge-v2-<split>.tables.md`) and `packages/evals/src/analysis/labelAttribution.ts` (`runs/evals/results/label-attribution.md`).

## Summary

- **Labels are fixed** (dataset `rec-v2.0`): the label is now the probability that an item is good over the pair-chemistry draw (`pGood`, Monte Carlo over 200 oracle seeds), the binary label is `pGood >= 0.5`, items are selected on that systematic label, and configurations that the hard gate would reject for an opt-out are no longer built. The gate-vs-oracle category-F disagreements are gone (0 by test).
- **The prompt fixes (pass 1 and pass 3 v3) did not survive the held-out test split.** On dev, where they were designed and tuned, the new gate > 1 > 3 pipeline beat the old one (76.6% vs 75.1% accuracy, Brier vs `pGood` 0.071 vs 0.081, p = 0.04). On the 532 untouched test items it lost: 71.2% vs **73.5%** accuracy (McNemar p = 0.32), precision 62.9% vs **68.8%** (-6.0 pp, 95% CI -11.1 to -1.0, p = 0.015), Brier 0.080 vs **0.073** (p = 0.13), AUC 0.789 vs **0.825**. Pass 1 v3 alone ties v2 (-0.6 pp, p = 0.86). Pass 3 v3 alone is worse than v2 (-4.5 pp model-only, p = 0.03; -2.1 pp with the gate, n.s.), though it abstains far less (2.1% vs 9.6%). The analysis's estimate of 73-74% from prompt fixes is not reached by the new prompts; the **old** pipeline is at 73.5% on the new labels.
- **Pass 2 with pass-3-style context is a large, significant win.** `judge-v3` vs `judge-v2.1` on test: +10.5 pp accuracy model-only (p < 0.001), +8.6 pp with the gate (70.1% vs 61.5%), precision +8.8 pp, Brier -0.039 (p < 0.001). Inside a pipeline it changes almost nothing: gate > 1 > 2 > 3 equals gate > 1 > 3 within 0.2 pp. The engine default for pass 2 is now the deep context (`judge.pass2Context: "deep"`).
- **Noise floor.** A same-prompt re-run of pass 1 v3 and the v3 pipeline on all 532 test items (fresh samples, 0 identical texts) flipped 11 of 532 pass-1 verdicts (2.1%); the re-run rows differ from the originals by +0.4 pp and 0.0 pp accuracy and by <= 0.0006 Brier. Here the prompt effects (120 discordant items for the pipelines) are well above that floor. The GEPA pilot measured a larger floor (about 1 in 5 verdicts flipping, -5 pp, n.s.) on its own setup, so differences of a few points on a few hundred items should be read with both numbers in mind; this report leans on the paired tests and on threshold-free metrics (Brier, log-loss, AUC).
- **Label fix vs prompt fix.** Re-scoring the old run's own verdicts against the new labels (no new calls) moves the old pipeline from 69.6% to 71.3% (70.9% on opt-in-consistent items), and its Brier from 0.196 against the old single-draw label to 0.093 against `pGood`. Nearly all of the improvement since 2026-10-06 is label and dataset, not prompts: the old prompts score 73.5% on the new test split, and the new prompts add nothing on test.
- **Recommended default pipeline:** hard gate > pass 1 (`pass1-screen-v2`) > pass 3 (`pass3-deep-v2`), with pass 2 on deep context if it stays in the engine flow. Passes 1 and 3 stay disabled in the engine by default, as before, until reviewer labels exist; the v3 prompts stay in the code for further evals.
- **Spend:** about $0.96 billed by Surplus (sum of `buyer_cost_micro` over the 4,926 new cached responses) plus 50 calls served by the OpenAI fallback (fractions of a cent at luna prices). The runner's spend guard, which counts every HTTP record including billed retries, summed to about $1.76. Either way under the $3 budget.

## 1. Label changes (dataset `rec-v2.0`)

Code: `packages/evals/src/recDataset.ts` (`buildRecDataset({ version: 2 })`), `packages/evals/src/worlds.ts`, `packages/evals/src/types.ts`. Version 1 is unchanged and still the default for the model-comparison suite.

- **Soft label.** `truth.pGood` = the probability that the oracle calls the configuration good, taken over the pair-chemistry draw. It is computed by Monte Carlo: the same configuration is evaluated by 200 oracles that differ only in seed (`<world oracle seed>:mc:<k>`). Chemistry is the only seeded part of `compatible`, so this is exactly the expected verdict. Policy-unsafe items get 0. No new oracle export was needed.
- **Binary label** = `pGood >= 0.5` (this is the "systematic" label: fit without chemistry). The old single-draw label is kept as `truth.drawnGood`.
- **Selection on fit.** Good and bad items are now selected on the binary label of the exact configuration that is built (same category), not on a single draw with no category. Good items can no longer be "good by a lucky draw".
- **Opt-in consistency.** A non-adversarial configuration is never built if an attending member has not opted into its category (or, for romance, has no romance opt-in). These are exactly the items the hard gate rejects and the oracle ignores. The 9 gate-vs-oracle disagreements of the old run (category F) cannot occur. Adversarial items (blocked, minor, romance without opt-in) are unchanged and labelled 0.
- **Data fixes already landed** (`2026-10-06-liveness-complementarity.md`) are in the labels: intent liveness, dating implies romance opt-in, and window presence. Dating anchors keep category `romance`.
- **Splits.** Dev = the four worlds the error analysis and the prompt fixes came from (sf-1, sf-2, nyc-1, nyc-2: 354 items). Test = six fresh worlds that nobody had looked at (sf-3, sf-4, sf-5 seeds 103-105; nyc-3, nyc-4, nyc-5 seeds 203-205; 532 items). Prompts were tuned only on dev. The test split was run once, with prompts frozen before any test result existed.
- **Deterministic and leak-tested.** `packages/evals/test/datasetV2.test.ts` checks: the binary label equals `pGood >= 0.5`; `pGood` agrees with an independent Monte Carlo on other seeds; the hard gate never rejects a non-adversarial item for an opt-out; the build is deterministic; and no v3 prompt contains canaries, names, ids, labels, `pGood`, source-truth words, boundaries or private disclosures (passes 1-2).

Composition: dev 354 items (294 pairs, 60 groups, 144 good, 56 policy-unsafe, 6 hidden-risk); test 532 items (442 pairs, 90 groups, 216 good, 84 policy-unsafe, 10 hidden-risk). The mean `pGood` is 0.35. On 65 dev and 94 test items, the single draw disagrees with `pGood >= 0.5`; 142 dev and 214 test items have `pGood` between 0.2 and 0.8.

## 2. Prompt changes

Code: `packages/engine/src/judgeCommon.ts` (`JUDGING_NOTES_V3`, `CODE_ENFORCED_V3`, `evidenceTag`, `boundaryRelevance`, `basisOf`), `judgeScreen.ts`, `judge.ts`, `judgeDeep.ts`. The old prompts stay exported (`SCREEN_SYSTEM_V2`, `JUDGE_SYSTEM`, `DEEP_SYSTEM_V2`, view option `version: "v2"`) so the old rows can be re-run on the new data.

| Pass | Old | New | Changes |
|---|---|---|---|
| 1 screen | `pass1-screen-v2` | `pass1-screen-v3` | Judges "would each person enjoy and benefit from meeting", not acceptance (`accept_probability` is still reported but does not decide). Each fact ends with `[basis via source, conf c, Nd old, HYPOTHESIS]`. Intents show their age, and expired intents are dropped. A redacted flag `private_boundary_relevant_to: ["format" \| "category" \| "topic"]` says that a private boundary touches that aspect of this configuration; the boundary text never leaves the builder. The shared v3 notes (below). The hard-policy list stays, so pass 1 alone is still policy-safe. |
| 2 rubric | `judge-v2.1` | `judge-v3` | Pass 3's context (every fact with basis, source, confidence, age and a hypothesis mark; live intents with age; logistics; edges) minus private context, which is replaced by the same redacted boundary flag. Same output schema, so the engine's score blend and floors are unchanged. Shared v3 notes. Selected in the engine by `judge.pass2Context: "deep"`. |
| 3 deep | `pass3-deep-v2` | `pass3-deep-v3` | Shared v3 notes. Private boundaries are penalties on `values_energy`, not vetoes, unless they are a hard dealbreaker for this exact intro; "a violated boundary" no longer defines `risk_safety` = 1. "Before you claim that a person has no relevant intent, re-read their intents list; a live intent outranks an inferred or old goal fact." Facts carry a `hypothesis` mark. Abstention questions about format, schedules or logistics are not allowed. `logistics` 3 = unknown schedules (normal). |

**Shared v3 judging notes** (all three passes):
- The question is whether every attending person would enjoy and benefit from meeting if it happens, not whether they accept today.
- Each person's gain must map to one of their own live intents or offers. One-sided fits are a no. A shared interest alone, which neither intent is about, is usually not enough.
- A shared or complementary stated intent is sufficient grounds; do not also require a shared hobby. *(Dev iteration 2:)* calibrate it: same broad intent and nothing else is only a little better than even (about 0.55-0.6).
- *(Dev iteration 2:)* Dating is the exception. The Network does not know who each person wants to date (gender, age range), so two dating intents alone are not enough: say no at about 0.25-0.3 unless the facts show each is looking for someone like the other.
- Groups are judged as a whole. *(Dev iteration 2:)* every member must get something from their own intents or clearly share the anchor; bigger groups of strangers need a stronger common purpose.
- Unknown schedules are normal. Reject on logistics only when meeting in the window is impossible.
- Facts show basis, source, confidence and age. An unconfirmed inferred or observed fact with confidence below 0.65 is a hypothesis and never the sole anchor. Facts older than 180 days may be stale.
- Private boundaries are penalties, not vetoes, unless a hard dealbreaker for this intro.
- *(Dev iteration 2:)* Most candidates are not good; if you say yes to nearly everything, you are too lenient.

Unchanged: explanation before verdict (all replies on all passes put it first), the member-facing leak gate, and the hard gate after every model verdict.

**Dev iteration 1 (rejected).** The first v3 notes swung too far. On dev, pass 1 said yes to about 85% of the items that pass the gate. Recall rose to 93%, but precision fell, and calibration worsened (ECE against `pGood` 0.24 vs 0.12; Brier 0.152 vs 0.100). The false positives were dating pairs (`pGood` averages 0.26 for dating pairs: who-wants-whom is never collected), groups, and friend pairs with nothing else in common. Iteration 2 added the three calibration notes marked above. Iteration-1 outputs: `runs/evals/results/judge-v2-dev-iter1.*`.

## 5. Recommended default pipeline

- **Pipeline:** hard gate > pass 1 (`pass1-screen-v2`) > pass 3 (`pass3-deep-v2`). Best accuracy, precision, AUC and Brier on test among the prompt sets measured: 73.5% accuracy, 68.8% precision, 63.4% recall, AUC 0.825, Brier vs `pGood` 0.073, 4.1% abstentions.
- **Pass 2:** use `judge-v3` (pass 3's context, no private context) wherever pass 2 runs. In the engine that is now the default (`judge.pass2Context: "deep"`, `packages/engine/src/config.ts`). Pass 2 adds nothing measurable on top of passes 1 and 3, so a pipeline that already runs pass 3 can skip it; removing it from the engine flow needs a change in `engine.ts` (pass 3 currently reviews pass-2 survivors), which is outside this work.
- **Engine defaults changed:** `judge.pass2Context` "compact" -> "deep". The engine's pass-1 and pass-3 prompts stay v2 (`SCREEN_SYSTEM` = `SCREEN_SYSTEM_V2`, `DEEP_SYSTEM` = `DEEP_SYSTEM_V2`); `judge.screen.enabled` and `judge.deep.enabled` stay false, as in the 2026-10-06 report, until reviewer labels exist.
- **Keep the v3 pieces that did not hurt:** the redacted boundary flag and the evidence notes are cheap and leak-tested; pass 3 v3's abstention rate (2.1% vs 9.6%) is closer to the prompt's own rule. They are not the default because the v3 rubric text as a whole lowered precision on test.
- **What to try next (not done here):** v2 prompts plus only the evidence notes and boundary flag (one change at a time, on a fresh test split); collect who-wants-whom for dating (dating pairs average `pGood` 0.26 and no prompt can see why); score pass-3 intent questions as "asked", not as false negatives.

## Caveats

- **The tree moved during this work.** The engine v1.2 work changed candidate generation and the simulator snapshot (events, shareable-interest consent, host tags, romance-preference facets) between dev iteration 1 and iteration 2. Iteration 1 and iteration 2 dev numbers therefore come from different item sets (165 of 354 dev items kept the same participants; 5 kept identical inputs). Dev iteration 2 and the test run share one code state. That state is now pinned: dataset-v2 worlds pass `snapshotFeatures: JUDGE_V2_SNAPSHOT_FEATURES` (`packages/evals/src/worlds.ts`), and the 2026-10-06 suites pass `LEGACY_SNAPSHOT_FEATURES`. After pinning, the dataset hash (sha256 of ids, configs and `pGood`) is unchanged (`3257024732c08dfc`) and all 886 pass-1 and pass-3 prompt inputs are byte-identical to the ones the runs used. The engine candidates still come from the current engine (`runEngine`), so a later engine change can still move dataset-v2 items.
- **Synthetic labels.** `pGood` is the oracle's own expected verdict. It removes the chemistry draw from the target, not the oracle's modelling assumptions.
- **One sample per prompt set**, at `reasoning_effort: medium`. The re-run arm puts the same-prompt noise at about 2% of verdicts on this setup.
- **Prompt tuning was one revision** (iteration 1 -> 2) on dev. The test split was not looked at before the prompts were frozen; dev iteration 2 and the test run were launched together after the freeze.
- **Abstentions count as "no".** The old pass 3 abstains on 9.6% of test items (11.6% of good, 8.2% of bad items), which costs it recall. Scoring abstentions separately ("asked") would raise the old pass 3's recall; see `abstainRate` in the summary JSON.
- **Tier strata are small** (minimal 60, rich 66, very_rich 10 on test). Treat per-tier differences as directional.
- **Pass 2 is evaluated on every item**, not in its native engine position (top-K after scoring).
- **Hidden-risk items** fell from 12 to 6 (dev) and 10 (test) because opt-in consistency removes some of their partners.
- Model calls went to Surplus, with the OpenAI fallback (now always on in `packages/core`) serving 50 calls after Surplus timeouts. Both serve gpt-6-luna.
