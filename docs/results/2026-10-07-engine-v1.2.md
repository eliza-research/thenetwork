# Engine v1.2: the match-failure recommendations, measured (2026-10-07)

Spec: [docs/research/2026-10-07-match-failures-and-diversity.md](../research/2026-10-07-match-failures-and-diversity.md) ("the report"). Every recommendation is a config flag in `packages/engine/src/config.ts` or a simulator snapshot feature in `packages/sim/src/snapshot.ts`. Each was measured against the corrected baseline, and only the ones that won are on by default. **No LLM calls, $0.** The judge passes were off. The tables are generated by `packages/engine/experiments/v12.ts`; the text is hand-written.

## Setup

| Item | Value |
|---|---|
| Baseline | `engine-v1.1.0` behaviour (`PRESETS.v1_1`, Normal 2/week), legacy snapshot (`LEGACY_SNAPSHOT_FEATURES`), the Network's own records fed back ("history fed": no re-asking a declined pair for 30 days). This is the report's "baseline + history" and reproduces it exactly: 251 proposals, 39.1%, 58.7%, 14.3, 19.9%, 19.6%, 0.470. |
| Simulator | 150 personas, 30 days, discrete, stub network, policy personas, seeds 1-8. "Richness" rows: the same with `richness: true`. |

| Harness check | `bun packages/engine/experiments/verify.ts`: traced engine == `runEngine` on the synthetic snapshot (218/218, byte-identical, v1.2 defaults); `selectX` == `selectProposals`. |
| Significance | From the report: over 8 seeds a precision difference under ~2.5 points is noise; met + worthwhile per seed needs a difference of 4 or more. Synthetic precision has a 95% CI of about ±6.5 points. |

```bash
bun packages/engine/experiments/v12.ts --sim-only                        # every sim variant, seeds 1-8
bun packages/engine/experiments/v12.ts --sim-only --only "^#1|^S3"       # selected variants (+ baseline)
bun packages/engine/experiments/v12.ts --richness --only "v1.2 defaults on the v1.2"
bun packages/engine/experiments/v12.ts --synthetic-only
bun scripts/synthetic/load.ts --engine                                   # rewrites data/synthetic/v1/engine_v1_run.json
```

**How the harness feeds the engine.** `runSim({ snapshot: { features, records: true } })` rebuilds each night's snapshot with `buildSnapshot(..., { features, records: world.records })`. That is exactly the call `packages/sim/src/world.ts` would make with proposal P1 below. With `records`, the snapshot carries `interactions` (with `acceptedBy` / `declinedBy` / `noResponse`), `feedback`, `openOpportunities` and `unsentProposalIds`, all rebuilt from what the Network itself recorded (`networkStateFromRecords`, a port of the report's `historyFromRecords`).

**Metric columns.** Precision = oracle-compatible share of proposals. Worthwhile = persona "worth a text" rate. Met + worthwhile = meetings held where everyone who came enjoyed it (≥ 0.5), per seed. Recall = latent good pairs proposed. No proposal = adults with no proposal in 30 days. Repeat pairs = sent pair proposals that repeat an earlier sent pair (includes intended second encounters). Invariants: minor contacts / canary leaks / invariant violations, summed over 8 seeds. Deltas in brackets are against the baseline row.

**Implemented, measured, off by default:** the acceptance ordering (#4), category overrides (#3), Normal 3/week (#5), ask before proposing (#7a), and the COMBO D preset (#8).

### 4. Order selection by score × √(estimated mutual acceptance) (off)

`config.acceptance` (exponent 0 = off; 0.5 measured). `world.ts acceptanceOf`: a Beta-smoothed share of invites the member said yes to (prior 0.45, weight 2), from `interactions[].acceptedBy / declinedBy / noResponse`. With `signals: true`, the prior also moves with participation state, unanswered proactive messages, `onlyWhenAsked`, recent proactive load and a want stated in the last 7 days. Selection orders eligible candidates by adjusted score × (Π P̂)^0.5; the threshold still applies to the score. No oracle, no hidden truth.

### 7. Ask before proposing (off) and the romance preference gate (on)

Engine output type `ask` (`EngineResult.asks: EngineAsk[]`, `policy.ts planAsks`). With `config.ask.enabled`, adults with no structured want or fewer than 3 matchable facets get one templated question. They are held back from proposals while it is open (`input.recentAsks`, 14-day cooldown); an answer (`answeredAt`) or silence past the cooldown releases them, so silence never locks a member out. With `config.romance.requireStatedPrefs` (on), romance is proposed only between members who both stated who they hope to meet, and a member with a live romance intent but no stated preferences gets the `romance_prefs` ask. Other proposals are not held back. The snapshot now carries romance preference tags (`romance:is/seeks/age`, agent_private) for opted-in members, except minimal-tier members, as the synthetic dataset does.

## Proposals for other owners (not done here)

- **P1 (sim `world.ts`, one line).** In `networkContext().snapshot()`, pass `records: this.records` to `buildSnapshot`. The engine then sees interactions, feedback, open opportunities and unsent proposals: no re-asking declined pairs (pair cooldown), `second_encounter`, response history, and dispatch awareness in the CLI.
