# Judgment passes: explanation-first passes 1-2 and a deep third pass (2026-10-06)

Model: **gpt-6-luna** on Surplus for every pass (founder decision: gpt-6-luna for everything). Request settings: `{"reasoning_effort":"medium","max_completion_tokens":4000,"max_completion_tokens_pass3":6000,"concurrency":4}`.

Reproduce: `bun run packages/evals/src/cli.ts --suite passes --models gpt-6-luna` (responses are cached under `runs/evals/cache/`, so reruns are free).

Dataset: 362 recommender items (302 pairs, 60 groups; 144 good, 56 policy-unsafe, 12 hidden-risk). Worlds: sf-1 (SF, seed 101, 320 personas, richness tiers + connected sources), sf-2 (SF, seed 102, 320 personas, richness tiers + connected sources), nyc-1 (NYC, seed 201, 320 personas, richness tiers + connected sources), nyc-2 (NYC, seed 202, 320 personas, richness tiers + connected sources).

> The "Summary", "Pass design", "Prompt iteration" and "Caveats" sections are hand-written. The tables are generated by `packages/evals/src/passReport.ts`, and regenerating the report replaces the hand-written sections with placeholders.

## Summary

- **The richness-tier data is in this run.** The dataset was rebuilt with the simulator's profile richness tiers and connected sources (`generatePersonas({ richness: true })`). Hidden truth and oracle labels are unchanged, but the Network now knows less about most people. The previous single-pass prompt scores **66.0%** on this data. On the older full-profile data it scored 67.8%. All comparisons below are paired on the same 362 items.
- **Pass 1, explanation before verdict, is a small, consistent improvement, but it is not statistically significant.** Accuracy is 68.5% vs 66.0% (+2.5 pp, McNemar p = 0.28) and precision is 58.5% vs 55.4% (+3.1 pp, bootstrap 95% CI -0.9 to +7.4). Calibration improves clearly: ECE drops from 0.140 to 0.073. On the old full-profile data, pass 1 scores 69.7% vs 67.8% (+1.9 pp, p = 0.34), with precision 59.0% vs 56.9% and ECE 0.072 vs 0.133. Cost is about 2.6x, because the model writes more and reasons longer: $0.126 vs $0.048 per 1,000 configurations. Latency p50 goes from 5.7 s to 8.9 s.
- **Pass 2, the engine rubric judge with explanation first, is the weak link.** On its own it scores 50.6% (AUC 0.52). With the hard gate it scores 58.0%, significantly worse than the baseline (p = 0.012). It sees the least context of the three passes: no ages, presence, edges or opt-ins, and only six do-not-quote facts per person. In the full pipeline it stops 42 of the 144 good items. **Putting pass 2 between pass 1 and pass 3 cuts recall to 37.5%** and only raises precision to 60.7%.
- **Pass 3, the deep review, is best used directly after pass 1.** The pipeline hard gate > pass 1 > pass 3 is the best configuration measured:

  | Metric | Gate > pass 1 > pass 3 | Previous single pass | Difference |
  |---|---|---|---|
  | Accuracy | 69.6% | 66.0% | +3.6 pp, p = 0.17 |
  | Precision | 62.0% | 55.4% | +6.6 pp, 95% CI +1.4 to +11.8, p = 0.009 |
  | Recall | 61.1% | 75.0% | -13.9 pp |
  | F1 | 0.615 | 0.637 | -0.022, n.s. |
  | ECE | 0.065 | 0.140 | |
  | Abstentions | 2.5% | 0% | |

  It is the only configuration with a **significant precision gain**, which is the weakness the founder flagged. It pays for it with recall. Pass 3 alone after the hard gate, without pass 1, is roughly a tie with the baseline: 68.0%, precision 57.4%.
- **Hard filters always win.** Every gated row rejects 56/56 policy-unsafe items. The models said "yes" on gated items 39 times in pass 2 and 19 times in pass 3. Both prompts tell the model that opt-ins and ages are enforced by code, and pass 2's input does not show them at all. The gate overrode every one of those answers.
- **Privacy:** member-facing text shows 0 canary or sensitive-fact leaks before and after the gate, and internal reasoning contains 0 canaries. The leak gate is strict. It rejected 132 of pass 3's member-facing texts, mostly for do-not-quote vocabulary, and the engine falls back to template explanations for those.
- **Spend:** this work spent about **$0.42** on Surplus. That is $0.41 in eval calls across all runs (smoke tests, the v1 prompts, the v2 prompts, the legacy-data pass-1 check) plus a few cents of live unit tests. The budget was $3.
- **Recommendation:** use pass 1 (explanation-first) as the default first look. Run pass 3 on pass-1 survivors when precision matters more than volume. That matches the PRD's precision gate for proactive proposals, so it applies during MVP review. **Do not chain pass 2 as currently built.** Either give it pass 3's context or drop it in favor of pass 1 > pass 3. In the engine, passes 1 and 3 ship disabled by default (`judge.screen.enabled`, `judge.deep.enabled`) until this has been checked against reviewer labels. Pass 2 remains on, as before.

## Pass design

There were two LLM judgments before this change, one per flow, and each was a single pass:
- the engine's rubric judge (`packages/engine/src/judge.ts`, top-K after deterministic scoring);
- the evals' recommender prompt (`rec-eval-v1`, the yes/no verdict in the model comparison).

This change follows the PRD's funnel ("a cheap model pre-screens; a strong model judges finalists") and names them:

| Pass | Code | Input | Output order (JSON keys) | Decision |
|---|---|---|---|---|
| 1. Screen (`pass1-screen-v2`) | `packages/engine/src/judgeScreen.ts`. It is the evals recommender, restructured. The public-view builder moved here so the engine and evals share it. | The public view: stated age, city, state, preferences, shareable facts, matchable facts (do-not-quote), intents, presence and explicit edges. No agent_private facts. | `reasoning` (fact-citing, by field such as `P1.intents[0]`), `cited_facts`, `dealbreaker`, **`verdict`**, **`match_probability`**, `accept_probability`, then `member_why` last (shareable only) | yes and no dealbreaker. In the engine, "no" gives `screen_reject` (off by default). |
| 2. Rubric judge (`judge-v2.1`) | `packages/engine/src/judge.ts`, restructured | The engine's scrubbed profile: up to 8 shareable and 6 do-not-quote facts, own request, state, formats, warm ties | `reasoning`, `cited_facts`, six 1-5 dimensions, `dealbreaker`, **`verdict`**, **`match_probability`**, `certainty`, then per-person `why` last | yes, no dealbreaker, all dimensions at or above the floor. In the engine, "no" gives `judge_reject` (`judge.verdictGates`). |
| 3. Deep review (`pass3-deep-v2`, new) | `packages/engine/src/judgeDeep.ts` | Every visible fact with basis, source, confidence and age. The basis is stated, confirmed, observed, inferred or vouched, and anything older than 180 days is flagged. Also: connected-source summaries (platform and status only), schedule overlap and shared areas, edges, mutual contacts and warm path, recent proposals, declines and feedback, budgets and recent asks, preferences, and agent_private context for internal judgment only (canaries redacted). | `evidence_review`, `steelman_for`, `steelman_against`, `rubric` (mutual benefit, reciprocity, intent and timing, logistics, stage fit, values and energy, novelty, evidence quality, risk and safety), `would_thank_us` per person, `reasoning`, `cited_facts`, **`verdict`** (yes / no / insufficient_information), `question_to_ask`, **`match_probability`**, then `member_why` last | Only "yes" proposes. "insufficient_information" withholds the candidate and logs the one question to ask. Pass 3 can only remove candidates. `hardGate` re-checks minors in any role, blocks, holds and opt-ins after the model. |

**Internal reasoning vs member-facing text.**
- Reasoning, steelmen and cited facts are internal. They are never shown to members, and the engine run log stores only a redacted, truncated synthesis.
- Member-facing text (`member_why` or `why`) is the last field. It passes `checkMemberFacing`, which rejects canaries, words found only in non-shareable or private facts, and contact details. If it fails, the engine uses its template explanation.
- Pass 3's clarifying question goes through the same gate before it is logged.

**Explanation first is verified.** The parsers check JSON key order. 100% of luna's replies on every pass put the explanation before the verdict.

## Prompt iteration (v1 to v2, passes 2 and 3 only)

The first run (`pass3-deep-v1`, `judge-v2`) made passes 2 and 3 far too strict:

| Row (v1 prompts) | Accuracy | Precision | Recall | Notes |
|---|---|---|---|---|
| Pass 2 | 58.0% | 44.6% | 22.9% | |
| Pass 3 | 63.8% | 60.3% | 26.4% | abstained on 27.9% of items |
| Pipeline: gate > 1 > 2 > 3 | 60.2% | | 7.6% | |

Reading the explanations showed two systematic errors, both double-counting:
- **Format.** A pair intro anchored on a group-shaped intent ("be part of a regular dinner group") was rejected because "the intent asks for a small group". It was also the most common abstention question.
- **Opt-ins.** Items were rejected for category opt-ins that code already enforces.

v2 adds the same three short "judging notes" to both prompts:
- Opt-ins, ages, blocks and budgets are enforced by code.
- An intro is a first step toward a group-shaped intent, and format is a soft signal unless the person's own format preferences exclude it.
- Thin evidence lowers confidence; it is not a "no" by itself.

v2 also tells pass 3 to abstain rarely. Pass 1 was not changed. The v1 per-item outputs are kept in `runs/evals/results/v1-passes-gpt-6-luna.*`. This was one revision informed by the eval set itself, so the v2 numbers for passes 2 and 3 are slightly optimistic. Pass 1's numbers are not affected.

## Per-item output for error analysis

- `runs/evals/results/passes-gpt-6-luna.items.jsonl`: one JSON object per item (all 362).
- `runs/evals/results/passes-gpt-6-luna.errors.jsonl`: the items where the pipeline or any single pass was wrong.
- `runs/evals/results/passes-gpt-6-luna.json`: raw per-pass results incl. HTTP records; `runs/evals/results/passes-gpt-6-luna.summary.json`: the metrics above.

Schema of each line: `{itemId, world, model, label: {good, unsafe, unsafeReason, hiddenRisk, oracleFlags, quality, minEnjoyment}, meta: {group, source, kind, category, objective, tier, proxyBucket}, hardGate, perPassVerdicts: {baseline, pass1, pass2, pass3, pipeline, pipelineStoppedAt}, correct: {baseline, pass1, pass2, pass3, pipeline}, confidence: {baseline, pass1, pass2, pass2Certainty, pass3}, explanations: {baseline, pass1: {reasoning, citedFacts, dealbreaker, memberWhy, reasoningFirst}, pass2: {reasoning, citedFacts, dimensions, dealbreaker, why}, pass3: {evidenceReview, steelmanFor, steelmanAgainst, rubric, wouldThankUs, reasoning, citedFacts, question, memberWhy}}, memberFacingAfterGate, leaks, refs, hidden: {byRef: {P1: {tier, sourceTruth: [{kind, value, source, truth, note}]}}}, visibleProfiles: {pass1, pass2, pass3}}`. `hidden` holds simulator hidden truth (each person's richness tier and the correct / stale / wrong_inference label of every connected-source fact) for error analysis only; it is never part of any prompt. `visibleProfiles` is exactly the user message each pass's model saw (parsed JSON; refs P1..Pn map to member ids via `refs`). Labels live only in this results file, never in a prompt.

## Caveats

- **Labels are the simulator oracle's, not real members'.** Roughly half of enjoyment variance is unpredictable pair chemistry by design. The absolute numbers matter less than the paired comparisons.
- **Small effects, single run.** Only pass 1 > pass 3's precision gain is significant at 0.05. Pass 1's gain over the baseline is consistent across both datasets (+2.5 pp and +1.9 pp), but it is not significant on either. All rows are a single sample at `reasoning_effort=medium`, and reruns without the cache would vary.
- **Tier strata are small.** There are 42 minimal, 127 light, 150 medium, 39 rich and 4 very_rich items. The item tier is the thinnest attending person's tier, so rich and very_rich items are rare. Treat per-tier differences as directional. Two directional findings:
  - On minimal-tier items, the gated pipeline proposes almost nothing (recall 24%), but what it proposes is right.
  - Pass 1 beats the baseline most on minimal and medium items.
- **The hard gate costs some oracle-good items.** It rejects 9 good items on category opt-in, which the oracle does not model. The dataset builder pairs people on intents in categories the helper never opted into. In production these would never reach a model, so the gated rows understate recall slightly compared with model-only rows.
- **History context is empty in this simulator snapshot.** Pass 3's rubric items for novelty and history (recent proposals, declines, feedback, interactions) have no data here, so this run does not exercise them. Unit tests cover the plumbing.
- **Pass 2 is evaluated outside its native position.** In the engine, pass 2 sees only the deterministic top-K. Here it judges every item, including random and adversarial ones, using the same thin input. Its poor standalone AUC is still a real signal that its input is too thin to discriminate.
- **Format for eval pairs** mirrors the engine's own rule (`intentFormat`): pairs anchored on a group-worded intent are labelled `small_group`, and that rule is part of what confused v1.
- **Cost and latency** are luna on Surplus with caching off for fresh calls. p95 latency for the full three-pass pipeline is 83.5 s per item, so it suits batch matching, not interactive use.
