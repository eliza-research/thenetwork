# Site builds with CRLF skill files

Date: 2026-10-29. Base: `a0ed7bc6495d9e524afc3d500738212a28dc7bc2`.
Environment: native Windows, PowerShell, Bun 1.4.2 (`744846f84`),
TypeScript 5.9.3. Dependencies use the frozen lockfile.

## Problem and scope

The current site build fails in a Windows checkout with `core.autocrlf=true`.
Git reports `i/lf w/crlf` for `sites/skills/ntwrk-party/SKILL.md`.
`skillDescription` only accepts LF frontmatter delimiters. It passes an empty
string to the YAML reader, then reads `description` from null. The build stops
before it writes the skill discovery index. The version reader has the same
LF-only delimiter and also needs the fix.

This fixes a reproduced build defect in the existing agent-first site path:
PRD 28.3 and 40, the MVP plan's agent-first onboarding, and `sites/README.md`
(the skill files and their discovery index). It adds no product requirement.

Both delimiters now accept LF or CRLF. The existing YAML reader, skill text,
published bytes, digest calculation, UI and prompts stay as they were.

## Reproduction and measurement

Run from the repository root with Bun 1.4.2:

```text
bun install --frozen-lockfile --ignore-scripts
bun test sites/test/skill-newlines.integration.test.ts
```

The one integration case copies the real site, router and required package
sources to a temporary tree. It writes all four skill sources with LF, builds
all four production sites, then repeats with CRLF. It checks the published
skill copies, a nonempty discovery description, the SHA-256 digest and the
filled landing-page agent row. It removes the temporary tree afterward.

| Same test, same sources | Before | After |
| --- | --- | --- |
| LF production builds | 4 succeeded | 4 succeeded |
| CRLF production builds | First build failed on `parsed.description` | 4 succeeded |
| Test result | 0 pass, 1 fail | 1 pass, 0 fail; 40 assertions |

The before run used the base `sites.ts` with the new integration case. The
after run used the two delimiter changes. Inputs and commands were the same.
This is a build result, not a statistical matching-quality result. Seed and
confidence interval: N/A. All test setup and this report are agent-authored;
the actual site artifacts are generated by the repository's build.

## Other checks and limits

- `bun run typecheck`: passed.
- `DEPLOY_TARGET=production bun run sites:build`: all four sites built on
  the native CRLF checkout. The build warned that no Turnstile site key was set.
- Full `bun run sim` on the base: 299/305 blocking gates passed. Six audit
  gates failed. The slop block passed 39/39 blocking gates.
- After the fix, `bun run sim --only audit`: 12/14 blocking gates passed.
  All four failed site-build gates now pass. The remaining two failures were
  already in the base run: the Observatory source-file scan finds no files on
  Windows, and Bash deploy-guard subprocesses return 127. PostgreSQL cases skip.
- `bun test sites/test/sites.test.ts`: 75 pass, 4 fail. Each remaining failure
  compares `walk()`'s Windows backslash paths with slash-separated paths. The
  site builds themselves succeeded.
- `bun run test:integration`: 358 pass, 252 skip, 30 fail. Failures include
  missing `initdb`/PostgreSQL, CRLF byte checks of the unchanged upstream
  contract mirrors, the Bash wrapper and the four path checks above. This is
  not a passing integration qualification.
- `bun run test:e2e`: 0 pass, 47 skip, 0 fail; PostgreSQL is not installed.
- `bun run plugins/build.ts --check`: failed on the three existing OpenAI
  YAML snapshots in the CRLF checkout. No plugin source or snapshot was edited.

The full simulation was run once, as the machine-load rule requires. Only the
affected audit block was repeated. No PostgreSQL, live-send or deploy result
is claimed. CI on Linux with PostgreSQL is still needed.

## Alternatives and attribution

1. Force LF with `.gitattributes`. This changes checkout policy and does not
   make the reader accept an otherwise valid CRLF skill file.
2. Normalize skill text before publication. This changes published bytes and
   their digests. Accepting both delimiters fixes parsing without that change.
